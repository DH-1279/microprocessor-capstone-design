## B. 민주: MediaPipe CPU 실행 방향은 맞지만 모델 파일은 필요함

**새로 손 모델을 학습하거나 Hailo용 HEF로 변환할 필요는 없다. 그러나 현재 코드에는 공식 사전학습 `hand_landmarker.task`가 필요하다.** `HandTracker.__init__()`이 `.task` 파일 존재를 확인하고 `BaseOptions(model_asset_path=...)`로 전달한다. 패키지 import만으로 준비가 끝나지 않는다. [Google Hand Landmarker Python 안내](https://developers.google.com/edge/mediapipe/solutions/vision/hand_landmarker/python)

우리가 선택한 구성은 **물체 인식은 AI HAT+ 2, 손 인식은 Pi CPU의 MediaPipe Tasks**다. 이 방향을 유지하며 객체 YOLO를 CPU에서 돌리는 우회는 이번 계획에 넣지 않는다.

사용자가 제공한 Pi 로그에서는 MediaPipe 1.0.1 import/API가 성공했지만 `.task`는 당시 없었다. 이후 파일 준비·모델 생성·실제 카메라 추론 여부는 추가 확인해야 한다. 장갑과 PCB가 부착된 손의 처리 시간·인식률도 실측 대상이다.

### C-1. 새 detector는 HEF를 사용하지 않음

`detector.py`는 `ultralytics.YOLO`로 `models/best.pt`를 로드하고, 주석에도 HailoRT 변경 예정이라고 적혀 있다. HEF 업로드와 실행 연결은 별개다. 현재 main의 **HailoDetector를 활용해 custom HEF와 라벨을 지정하는 방식**이 중복 실행기 작성보다 낫다.

KHS 코드는 공통 `Detection` 대신 임시 클래스를 사용하고 메서드도 `process()`여서 공통 `detect(rgb)` 계약과 정리가 필요하다. `.pt` 단독 실험은 웹캠·GUI 방식이며 HAT 실행 명령으로 안내하지 않는다.

RGB NumPy 배열을 YOLO에 그대로 전달하는 문제도 있다. Ultralytics NumPy 입력은 BGR이므로 해당 실험을 유지한다면 RGB→BGR 변환을 넣어야 한다. 이것을 고쳐 CPU YOLO로 우회하는 것은 이번 MVP 방향이 아니다. [Ultralytics 입력 계약](https://docs.ultralytics.com/modes/predict/#inference-sources)

metadata의 출력 인덱스 순서는 다음과 같다. 대소문자·공백을 유지한 18행 labels 파일이 필요하다.

추가 재현에서 **override의 targets에서 book을 생략해도 공통 `_merge()`가 기존 book을 유지**했다. 단순 생략으로 제거되지 않으므로 대상 사전 교체 계약 또는 모델별 기본 설정을 먼저 마련한다. 지금 HEF 경로만 바꾸고 `run`을 실행하는 절차는 완성되지 않았다.

### C-3. SDK 차이는 Pi에서 검사해야 함

사용자가 확인한 Pi CLI·펌웨어는 **5.1.1**, 모델 컴파일 SDK는 **5.4.0**이다. 버전 차이만으로 반드시 실패한다고 단정하지 않는다. 실제 로딩·지원 기능·입출력 계약·추론을 확인해야 한다. [HailoRT 모델 버전 검증 구현](https://github.com/hailo-ai/hailort/blob/v5.1.1/hailort/libhailort/src/hef/hef.cpp)

호환 오류가 나면 현재 Pi 스택용 재컴파일 또는 공식 지원 스택의 SDK·드라이버·펌웨어·Python 바인딩 정합을 선택한다. 검사 전에 임의 업그레이드하거나 버전 검사를 무시하는 옵션으로 우회하지 않는다. HEF의 추정 FPS는 Pi 카메라 포함 실제 성능이 아니다.

## E. 머지 없이 해수 모델을 Pi에서 검사하는 방법

기존 변경은 `git status --short`로 먼저 확인한다. 다음은 팀원 브랜치를 checkout하지 않고 모델만 임시 경로에 꺼내는 Linux 명령이다.

```bash
cd "$HOME/Desktop/kimGA_raspi/microprocessor-capstone-design/03. 김가네 캡스톤 디자인/Raspi5_vision"
git status --short
git fetch origin
source .venv/bin/activate
mkdir -p /tmp/kimgane-khs-review
git show 'origin/seawater0414/2026-10-14:03. 김가네 캡스톤 디자인/Raspi5_vision/KHS_object_detection/best_hailo_model/best.hef' > /tmp/kimgane-khs-review/best.hef
sha256sum /tmp/kimgane-khs-review/best.hef
hailortcli --version
hailortcli fw-control identify
timeout 20s hailortcli parse-hef /tmp/kimgane-khs-review/best.hef
```

해시를 C절과 비교하고, parse 실패 시 전체 로그를 기록한다. 성공한 뒤에는 현재 공통 HailoDetector를 이용해 configure·실제 카메라 추론을 검사한다. 다음 코드는 설정을 메모리에서만 복사하고 BLE·controller를 실행하지 않는 단독 시험이다.

```bash
timeout 60s python - <<'PY'
from pathlib import Path
from contextlib import ExitStack
from haptic_mvp.config import load_config
from haptic_mvp.vision import HailoDetector, CameraSource

labels = ('bottle', 'cell phone', 'cup', 'handbag', 'keyboard', 'laptop',
          'mouse', 'remote', 'scissors', 'tie', 'Glasses', 'key',
          'Medicine', 'Tumbler', 'Pen', 'Wallet', 'watch', 'Wireless Earbud')
path = Path('/tmp/kimgane-khs-review/labels.txt')
path.write_text('\n'.join(labels) + '\n', encoding='utf-8')
config = dict(load_config()['vision'])
config.update(object_model='/tmp/kimgane-khs-review/best.hef', labels_file=str(path))
with ExitStack() as resources:
    detector = resources.enter_context(HailoDetector(config))
    print('Hailo configured:', detector.model_width, detector.model_height,
          'classes:', len(detector.labels), flush=True)
    camera = resources.enter_context(CameraSource(config))
    for index in range(10):
        item = camera.read()
        if item is None:
            raise RuntimeError('No camera frame')
        rgb, captured_at = item
        print(index, detector.detect(rgb), flush=True)
PY
```

컵·물병·마우스를 보여주고 라벨·좌표·출력 오류를 확인한다. 이 절차는 Pi에서 아직 실행하지 않았으므로 성공했다고 기록하지 않는다. 빈 탐지 결과만 나온 것은 인식 품질 검증이 아니다.

손 모델은 [VISION_SETUP.md](../Raspi5_vision/VISION_SETUP.md)의 공식 `.task` 다운로드와 모델 생성 절차를 따른다. 이미 다운로드했다면 덮어쓰기 전에 경로·해시부터 확인한다. 손은 공통 MediaPipeHandTracker로 먼저 단독 시험하고, 민주 보정 코드는 수정 후 같은 프레임으로 비교한다.

### KMJ-1 · P1 · 웹 화면의 WebSocket이 연결되지 않음

위치: [`ui/server.py:182`](https://github.com/DH-1279/microprocessor-capstone-design/blob/656f6206fbf9e070b47d4a8fcd21963dfbaf76eb/03.%20김가네%20캡스톤%20디자인/Raspi5_vision/KMJ_hand_audio_ui/ui/server.py#L182)

파일은 postponed annotations를 사용하지만 `WebSocket`을 `build_app()` 내부에서 import한다. 점검한 FastAPI는 `socket: WebSocket` 타입을 해석하지 못하고 `socket`을 필수 query parameter로 취급했다.

실제 FastAPI 앱을 TestClient로 구성한 결과:

```text
GET /                 -> 200
GET /api/state        -> 200
POST /api/command     -> stop 요청 전달 성공
WebSocket /ws         -> 연결 거부, code=1008
reason                -> query.socket: Field required
route query parameters -> ['socket']
```

메모리에서만 타입 이름을 해석 가능하게 바꾸자 query parameter가 없어지고 `/ws`에서 `scanning` 상태 수신이 됐다. 브랜치 파일은 고치지 않았다.

**수정 방향:** 라우트의 WebSocket annotation이 실제 타입으로 해석되게 한다. 이 파일의 future annotations 사용을 조정하거나 타입을 올바르게 노출하되, 웹 의존성이 없는 경우에도 다른 모듈이 import되는 조건을 유지한다. HTTP 계약 테스트 외에 WebSocket 연결·상태 수신·정지 전송 테스트를 추가한다.

또한 README의 `pip install fastapi uvicorn`만 설치한 점검 환경에는 `websockets`·`wsproto`가 없었다. 실제 Uvicorn 서버에서도 WebSocket을 쓰려면 예를 들어 `uvicorn[standard]`처럼 지원 백엔드가 포함된 설치 요구를 명시하고 버전을 기록해야 한다. TestClient 성공과 실제 Uvicorn 연결 성공을 각각 확인한다.

위치: [`tools/stt_bench.py:35`](https://github.com/DH-1279/microprocessor-capstone-design/blob/656f6206fbf9e070b47d4a8fcd21963dfbaf76eb/03.%20김가네%20캡스톤%20디자인/Raspi5_vision/KMJ_hand_audio_ui/tools/stt_bench.py#L35)

```python
from command_mapper import parse, STATES
```

해당 `command_mapper.py`가 저장소에 없다. NumPy·sounddevice를 대역으로 제공하고 시작 경로를 실행해도 `ModuleNotFoundError: No module named 'command_mapper'`가 재현된다. 실제 오디오 라이브러리 설치만으로 해결되지 않는다.

도구 내부는 `parse(text, state="전체")` 같은 이전 API와 `phone` 라벨을 사용하지만 새 `speech.py`는 targets 입력, 영어 상태 이름, `cell phone` 라벨을 사용한다. 따라서 import 한 줄을 바꾸는 것만으로 수정이 끝나지 않는다. 새 명령 파서의 계약에 맞게 호출·기대 라벨을 함께 바꾸고, 도구가 `--help`·`--list`로 시작하는 테스트를 추가한다.

### KMJ-3 · P1 · 실제 Tracker 경로에서 좌우 다수결 보정이 적용되지 않음

위치: [`hand_tracker.py:255`](https://github.com/DH-1279/microprocessor-capstone-design/blob/656f6206fbf9e070b47d4a8fcd21963dfbaf76eb/03.%20김가네%20캡스톤%20디자인/Raspi5_vision/KMJ_hand_audio_ui/hand_tracker.py#L255)

`detect()`는 `hand_from_result(result, self.selected, ...)`를 먼저 호출한다. 기본 `Right` 설정에서 MediaPipe가 한 프레임을 `Left`로 잘못 분류하면 그 결과를 `None`으로 버린 뒤 stabilizer에 전달한다. 따라서 stabilizer는 반대쪽 표를 보지 못한다.

MediaPipe 대역을 이용해 실제 `HandTracker.detect()` 호출 경로를 재현했다.

```text
프레임 0: Right, x=0.2 -> x=0.2
프레임 1: Left,  x=0.8 -> x=0.2 (이전 위치 유지)
flips_absorbed=0, held=1, votes=['Right']
```

기존 handedness 단위 테스트는 `HandStabilizer`에 직접 raw Hand를 넣어 통과하지만, 실제 Tracker에서는 다른 경로를 탄다. **투표에 필요한 판정을 버리기 전에 전달하고, 모호한 복수 손과 실제 다른 손으로의 전환을 구분하는 선택 정책을 유지해야 한다.** 단순히 아무 손이나 허용하는 우회는 피한다. 움직이는 대표점·뒤집힌 판정·복수 손을 실제 `detect()` 경로로 시험한다.

### KMJ-4 · P1 · 안내된 손 보정 설정을 공통 로더가 거부함

README는 `vision.hand_stability.hold_ms: 0`으로 유지 기능을 끌 수 있다고 안내한다. 하지만 공통 config에는 `hand_stability` 키가 없고, 알려지지 않은 키를 거부한다.

```json
{"vision": {"hand_stability": {"hold_ms": 0}}}
```

이 override를 `load_config()`에 전달하면 다음 오류가 난다.

```text
Unknown configuration key: vision.hand_stability
```

공통 설정 기본값·검증·문서를 함께 추가한 뒤 사용해야 한다. 특히 기본 400ms 유지 기능은 이전 측정점을 새 프레임의 손 결과로 반환하므로, 프레임이 최신이라는 이유만으로 손 좌표도 최신이라고 판단하면 안 된다. 내일 모터 연결 전에는 유지 기능을 끈 기본 경로로 시작하고, 유지 여부·손 좌표의 실제 측정 시각과 정지 정책을 먼저 정한다.

### KMJ-5 · P2 · 상태별 UI 명령 제한과 공통 상태 전이가 연결되지 않음

위치: `ui/server.py:137`, `speech.py`의 `STATE_COMMANDS`, 진행 MD의 controller 연결 예제.

`Bridge.handle()`은 `parse_input(raw, targets)`를 상태 인자 없이 호출한다. `guiding`에서 버튼 목록에는 물건 선택이 없는데 API로 `select_book`을 보내면 `accepted=True`로 책 요청이 전달되는 것을 재현했다. 문서대로 새 controller 파서를 연결하면 최종 거부는 가능하지만, 현재 브랜치에는 그 연결이 없다.

또한 제안된 `_intent_state()`는 `confirming`·`waiting`·`near`를 반환하지 않는다. 새 파서의 시작·재개·완료 명령은 이 상태를 요구하므로 연결 예제만 붙여서는 해당 UX가 완성되지 않는다. 현재 공통 상태는 `guiding + reason=near`다.

같은 종류의 물체가 여러 개일 때 사용할 좌우 선택 버튼도 현재 HTML에 없다. 공통 상태·허용 명령·버튼·controller 전이를 한 계약으로 맞춰 시나리오 테스트를 추가한다. 공통 코드가 연결 전임을 문서에 적은 것은 올바르지만, 내일 바로 완성된 UX로 실행할 수 있다는 뜻은 아니다.

### KMJ-6 · P2 · 손 측정 도구는 현재 CSI 카메라 절차와 맞지 않음

위치: `tools/hand_bench.py:35`, `119`.

모델 경로는 작업 디렉터리의 `hand_landmarker.task`인데 프로젝트 설치 경로는 `models/hand_landmarker.task`다. 카메라 입력은 `cv2.VideoCapture(0)`의 웹캠 방식이고 Camera Module 3용 Picamera2 경로가 없다. GUI도 사용하므로 SSH 단독 실행 절차와 맞지 않는다.

이 도구는 노트북 웹캠용임을 문서가 밝히고 있으므로 과거 측정을 잘못된 것으로 취급하지 않는다. 다만 **내일 Pi 손 인식 벤치 명령으로 그대로 안내하지 않는다.** 모델 경로·CSI 입력·headless 측정 옵션을 추가하거나 공통 카메라 입력을 이용하는 Pi 전용 측정 도구를 마련한다. 파일·카메라 실패 시 성공 종료 코드로 끝나는 부분도 수정한다.

### KMJ-7 · P2 · TTS 캐시 키는 같지만 실제 안내 문장이 일치하지 않음

`prebuild_tts.cache_name()`과 공통 `tts_cache_path()`의 해시 규칙은 일치했다. 하지만 실제 controller가 내보내는 다음 문장들은 사전 생성 목록에 없었다.

```text
안내를 중지했습니다.
마우스을 찾아 안내하겠습니다.
휴대전화을 찾아 안내하겠습니다.
```

이는 현재 controller의 조사·문구와 사전 생성 도구가 사용하는 문구가 다르기 때문이다. 해시만 같아도 텍스트가 다르면 런타임은 다시 합성한다. 공통 문장 생성기를 사용하고 실제 안내 시나리오의 캐시 적중 여부를 시험한다. 동적으로 조합되는 물체 목록도 별도 고려한다. ‘실행 중 합성이 사라진다’는 설명은 전체 문장 일치가 확인된 범위로 제한한다.

### 바로 확인할 수 있는 KMJ 명령

Pi에서 KMJ 브랜치 또는 해당 변경이 반영된 코드의 `Raspi5_vision` 폴더에서 실행한다. main에 아직 없는 코드를 main에서 바로 실행할 수 있다고 가정하지 않는다.

```bash

python3 -m KMJ_hand_audio_ui.tools.console_check
```

문서의 `python -m unittest discover tests`는 기존 모든 테스트까지 불러오므로 69개 신규 테스트만 실행하는 명령이 아니다. 기존 `test_runtime.py` 등은 pytest를 import하며 pytest가 없는 환경에서 import 오류가 나는 것을 확인했다. 신규 KMJ 검사만 하려면 위처럼 범위를 지정하고, 전체 검사는 개발 의존성을 설치한 환경에서 `python -m pytest -q`로 수행한다.

## 6. 팀원에게 요청할 수정 사항

**김해수:** 실제 객체 인식 코드를 먼저 올리고, 모델을 다른 팀원이 받을 수 있는 방법과 HAT 변환·18개 클래스의 정확한 출력 순서를 정리한다. `2026-10-13_KHS_객체인식.md`에 실행 명령·환경·성능·미검증 항목을 작성하고 결과 사진을 연결한다. 사진에서 탐지 상자가 나온 사실을 전체 클래스 정확도나 Pi 실시간 성능으로 확대하지 않는다.

**김민주:** WebSocket 타입 해석과 백엔드 의존성, STT 도구의 누락 import·API, Tracker의 필터/투표 순서를 우선 수정한다. 손 보정 설정은 공통 config 변경과 함께 검토하고, 캐시 문장과 실제 안내 문구를 맞춘다. 테스트 명령을 범위별로 구분하고 Ruff·Mypy 오류도 정리한다.

**김동환 통합 작업:** 수정된 담당 모듈을 공통 카메라·데이터·명령 경로에 연결한다. 목표 선택·동일 물체 좌우 선택·명시적 시작·손 손실·재개·중지·연결 만료를 시나리오로 시험한다. 통합 전 기본 테스트 통과와 통합 후 실제 사용자 흐름 통과를 각각 기록한다.

현재 의견은 **두 PR 모두 수정 후 다시 검토하는 것**이다. 수정 커밋이 올라오면 변경 부분과 실패했던 재현 사례를 다시 확인하고, 이후 Pi에서 실행한 로그를 기준으로 통합 여부를 판단한다. 이번 리뷰에서는 PR에 댓글을 보내거나 팀원에게 메시지를 전송하지 않았다.

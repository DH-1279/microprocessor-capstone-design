# 손 인식 · 프론트 · 음성 파트 조사

- 작성일: 2026-09-29
- 담당: 김민주
- 담당 파트: 1. 핸드 인식 + 4. 프론트·TTS·STT
- 상태: 문헌 조사 완료, 실기기 검증 미수행

이 문서는 조사한 내용과 실제로 검증한 결과를 구분해 기록한다. 아래 2장의 수치와 사례는 모두 공개된 논문·문서에서 인용한 것이며, 본 프로젝트 환경에서 직접 측정하지 않았다. 추정에 해당하는 서술은 그때마다 명시했다.

## 1. 담당 파트와 MVP 범위

### 1-1. 담당 범위

| 파트 | 내용 |
|---|---|
| 핸드 인식 | 카메라 영상에서 손의 위치를 추출 |
| STT | 한국어 음성 명령을 텍스트로 변환하고 명령으로 확정 |
| TTS | 안내 문장을 음성으로 출력 |
| 프론트 | 손·물체 인식 상태와 안내 상태를 표시 |

### 1-2. 8주차 시연 목표

**장갑을 착용한 사용자가 음성으로 물체를 지정하고, 손이 목표에 도달할 때까지 안내받는 전 과정이 끊김 없이 동작하는 상태를 목표로 한다.**

시연 흐름에서 본 파트가 담당하는 구간은 다음과 같다.

```
착용 → "컵 찾아줘" ──[STT]──→ 명령 확정
                                  ↓
     손 추적 ──[핸드 인식]──→ controller.py → 진동 안내
                                  ↓
            "컵을 찾아 안내하겠습니다" ──[TTS]──→ 스피커
                                  ↓
                   진행 상황 ──[프론트]──→ 화면
```

### 1-3. 항목별 완성 기준

| 항목 | 완성으로 보는 기준 |
|---|---|
| 핸드 인식 | 장갑 착용 상태에서 손 위치가 안정적으로 산출된다 |
| STT | 9개 명령의 인식 성공률 90% 이상 |
| TTS | 물체명과 주요 안내 문장을 알아들을 수 있다 |
| 프론트 | 인식 상태와 안내 방향을 화면으로 확인할 수 있다 |
| 전체 | 각 기능이 동시에 동작하며 서로의 처리를 막지 않는다 |

### 1-4. 가장 큰 변수 — 장갑 착용 인식

본 파트에서 결과를 예측하기 어려운 항목은 장갑 착용 상태의 손 인식 하나다. 나머지는 부품 수령 후 구현과 측정을 반복하면 달성 가능한 범위로 본다.

MediaPipe가 장갑 낀 손의 키포인트를 전혀 검출하지 못했다는 보고가 있으며(2-4 참조), 여기에 모터와 PCB까지 부착되면 조건이 더 불리해진다. 따라서 단계별 대응을 준비한다.

| 단계 | 조건 | 대응 |
|---|---|---|
| 1 | 장갑 착용 상태에서 인식이 충분함 | 그대로 진행 |
| 2 | 인식률이 부족함 | 검출기 보강(B안). 손 영역을 먼저 찾아 MediaPipe에 전달 |
| 3 | B안으로도 부족함 | MC-hands-1M으로 파인튜닝(C안) |
| 4 | 파인튜닝 모델의 파이 구동이 불가함 | 맨손 시연으로 축소. 장갑 인식은 후속 과제로 명시 |

**3단계를 실행 가능한 선택지로 둔다.** MC-hands-1M은 오른손 장갑 착용 합성 이미지 100만 장으로 본 과제가 오른손을 기준으로 하는 점과 맞으며, 해당 데이터셋으로 공개 손 관절 검출 모델을 파인튜닝해 합성·실제 이미지 양쪽에서 성능을 확보했다는 보고가 있다. 데이터를 직접 수집·라벨링할 필요가 없어 학습 자체는 2~3주 내에 시도할 수 있을 것으로 본다. 학습은 개발 PC나 클라우드 환경에서 수행하므로 파이 작업과 병행 가능하다.

다만 학습한 모델을 AI HAT에서 구동하려면 변환이 필요하며, 이 과정의 성공 여부는 확인되지 않았다. 4단계는 이 경우를 대비한 최후 수단이다.

**장갑 시제품이 나오는 대로 인식률을 우선 측정해 어느 단계로 갈지 일찍 결정한다.** 3단계로 가야 한다면 학습 기간을 확보해야 하므로 판단이 늦을수록 불리하다.

### 1-5. 후속으로 미루는 항목

| 항목 | 사유 |
|---|---|
| 손가락 관절 단위 제스처 인식 | 현재 설계에서 사용하지 않음 |
| 자유 문장 음성 명령 | 고정 어휘로 충분하며, LLM 연동은 팀 문서상 확장 방향 |
| 배속 재생 시 음질 개선 | 별도 음성 모델이 필요 |
| 안내 중 음성 끼어들기 | 반향 제거 등 추가 처리 필요 |
| 화면을 통한 물체 선택 | 사용자가 시각장애인이므로 주 입력 경로가 될 수 없음 |

## 2. 손 인식

### 2-1. 요구 조건

본 시스템에서 손 인식이 제공해야 하는 정보는 다음과 같다.

| 필요 정보 | 용도 |
|---|---|
| 손의 화면상 위치 | 물체와의 상대 벡터 계산 |
| 손의 회전각 | 진동 방향을 손 기준으로 변환 |
| 손등·손바닥 구분 | 뒤집힘 시 좌우 모터 반전 |
| 좌우 손 구분 | 오른손만 추적 |

현재 MVP 범위에서는 손 기준점만 사용하므로 정밀한 관절 각도는 필요하지 않다. 다만 파지 완료 판정 등으로 확장할 경우 관절 정보가 필요해질 수 있어, 관절 좌표를 제공하는 모델을 후보로 유지한다.

### 2-2. 후보 선정 및 비교

**선정 기준**

| 기준 | 이유 |
|---|---|
| 관절 좌표 제공 | 손 기준점 계산과 후속 확장 대비. 단순 바운딩박스만으로는 부족 |
| 라즈베리파이 구동 가능성 | 최종 장치가 파이 5 + AI HAT+ 2로 확정 |
| 장갑 착용 대응 | 본 프로젝트의 핵심 제약 조건 |
| 자료 접근성 | 학기 내 구현해야 하므로 문서와 사례가 확보되어야 함 |

**후보 선정 이유**

| 후보 | 선정 이유 |
|---|---|

| WiLoR | MediaPipe와 동일 조건에서 직접 비교한 연구가 있어 성능 차이를 수치로 확인 가능 |
| RTMPose 계열 | 장갑 착용 환경(수술실)에 적용한 사례가 있음 |
| 자체 학습 모델 | 장갑 문제의 근본 해결책. 비교 기준선으로 포함 |

**비교**

| 후보 | 방식 | 라즈베리파이 구동 | 장갑 대응 | 비고 |
|---|---|---|---|---|
| MediaPipe Hands | 손바닥 검출 → 21개 랜드마크 회귀 | 가능 (공식 Pi 예제 제공) | 실패 보고 다수 | 자료 풍부, 경량 |
| WiLoR | YOLO 계열 검출 + ViT 기반 3D 복원 | 미확인 | 가려짐에 상대적으로 강함 | 연산량 큼 |
| RTMPose 계열 | 전신 자세로 손 위치 초기화 후 크롭 | 미확인 | 수술 환경 적용 사례 있음 | 다단계 파이프라인 |
| 자체 학습 모델 | 장갑 데이터로 직접 학습 | 설계에 따라 다름 | 대응 가능 | 데이터 수집·라벨링 필요 |

WiLoR와 RTMPose의 라즈베리파이 구동 가능 여부는 확인하지 못했다. 두 모델 모두 MediaPipe보다 연산량이 크므로 AI HAT 없이는 어려울 것으로 보이나, 실측하거나 문헌으로 확인한 값은 없다.

### 2-3. MediaPipe의 구조와 출력

MediaPipe Hand Landmarker는 두 모델로 구성된다. 손바닥 검출 모델이 전체 이미지에서 손 영역을 찾고, 손 랜드마크 모델이 그 크롭 영역에서 21개 키포인트를 산출한다. 손바닥 검출은 연산이 무겁기 때문에, 영상·스트림 모드에서는 이전 프레임의 랜드마크로 다음 프레임의 손 영역을 잡고, 추적에 실패했을 때만 손바닥 검출을 다시 실행한다.

출력은 세 가지다.

- 이미지 좌표 랜드마크 21개
- 월드 좌표 랜드마크 21개
- handedness (왼손/오른손)

### 2-4. 핵심 문제 1 — 장갑 착용 시 인식 실패

본 파트에서 가장 먼저 해결해야 할 문제다.

**확인된 사례**

| 출처 | 내용 |
|---|---|
| MDPI Sensors, 2024 (의료용 장갑) | MediaPipe Hands로 장갑 낀 손을 추적하려 했으나 키포인트를 전혀 검출하지 못하고 전부 NULL을 반환했다. 다른 모델로도 장갑 낀 손의 점을 추론할 수 없었다고 보고 |
| arXiv, 손 검출 데이터 연구 | 실제(장갑 착용) 이미지에서 MediaPipe가 손을 하나라도 찾은 비율이 0.414에 그쳤으며, 이는 실제 장갑 낀 손도 많이 놓친다는 뜻이라고 기술 |
| arXiv 2407.14903 (임상 제스처) | MediaPipe의 손 검출 정확도가 57.6%인 반면 YOLOv7 손 검출기는 99.8%였음 |
| arXiv 2601.15918 (수술실 3D 손 포즈) | 장갑으로 인해 손 외형이 균일해지는 것을 주요 난점으로 명시 |

**원인**

MC-hands-1M 논문(arXiv 2210.10428)은 원인을 명확히 지적한다. 맨손 데이터셋으로 학습된 기존 손 검출·추적 알고리즘은 장갑 상황에서 성능이 크게 떨어지거나 완전히 실패하며, 이는 사람 피부색이라는 바탕에 깊이 의존하기 때문이다.

즉 모델이 피부색을 주요 단서로 손을 찾고 있어, 장갑이 그 단서를 가리면 검출 자체가 무너진다.

#### 대응 방안

**A. 장갑 설계 조정**

장갑 색상이나 노출 범위를 조정해 인식률을 확보하는 방안. 본 프로젝트는 장갑을 직접 제작하므로 정해진 장갑을 써야 하는 제약이 없다.

다만 부분 노출이 인식에 도움이 되는지는 확인된 근거가 없다. 조사한 문헌은 모두 장갑을 완전히 착용한 조건이었다. MediaPipe가 손바닥 검출을 먼저 수행하는 구조임을 고려하면, 손가락 일부만 노출해도 검출 단계에서 실패할 가능성이 있다. 또한 모터가 손가락에 부착되므로 노출 가능한 범위 자체가 제한되고, 노출 구조는 장갑을 잘라야 하므로 되돌릴 수 없다.

이 방안은 추가 검토가 필요하며, 색상 조정부터 우선 적용한다.

**B. 검출기 보강**

YOLO 계열 검출기로 손 영역을 먼저 찾고, 그 크롭을 MediaPipe에 전달하는 방식.

근거는 두 가지다. 임상 제스처 연구에서 MediaPipe의 손 검출 정확도가 57.6%인 반면 YOLOv7 손 검출기는 99.8%였으며, 해당 연구는 YOLOv7으로 손 영역을 찾아 MediaPipe에 넘기는 구성을 채택했다. 수술실 3D 손 포즈 연구도 동일한 발상으로, 도메인 특화 파인튜닝 없이 공개 사전학습 모델만 조합해 처리했다. 구체적으로는 YOLOv11x로 사람을 검출하고, RTMPose-Wholebody로 손 위치를 대략 초기화한 뒤, 추적으로 손 바운딩박스를 유지하고, 그 크롭에 고해상도 손 포즈 모델을 적용한다.

핵심은 손을 직접 찾지 않고 다른 단서로 위치를 먼저 잡은 뒤 크롭해서 넘긴다는 것이며, 장갑으로 손바닥 검출이 실패하는 문제를 우회한다.

**C. 파인튜닝**

MC-hands-1M 데이터셋으로 장갑 착용 손을 추가 학습하는 방안. 해당 데이터셋은 오른손 장갑 착용 합성 이미지 100만 장이며, 공개 손 관절 검출 모델을 파인튜닝해 합성 이미지와 실제 장갑 착용 이미지 양쪽에서 성능을 확보했다고 보고한다. 본 프로젝트가 오른손을 기준으로 하는 점과 맞는다.

**D. 전용 모델 개발**

장갑 데이터를 직접 수집·학습하는 방안. MDPI 연구는 자체 모델로 평균 오차 5픽셀 미만을 달성했고, 신뢰도 60% 미만 키포인트를 제외하면 RMSE 7.48픽셀이었다.

#### 선택

**B(검출기 보강)를 기본안으로 한다.**

- 조사한 방안 중 유일하게 근거가 확인된 방법이다. 동일한 발상을 채택한 연구가 둘 있고, 검출 정확도 차이가 수치로 제시되어 있다.
- 모델을 교체하지 않고 앞단만 추가하는 구조라 기존 코드를 유지할 수 있다.
- 장갑을 어떤 형태로 만들든 독립적으로 동작한다.

**A는 색상 조정부터 병행한다.** 추가 개발 비용이 없다는 장점은 있으나 효과가 확인되지 않았고, 노출 구조는 되돌릴 수 없으므로 신중히 판단한다.

**C는 B로 부족할 경우의 차선안으로 둔다.** 학습 환경 구성과 시간이 필요하지만, MC-hands-1M을 사용하면 데이터 수집·라벨링을 건너뛸 수 있어 8주차 내에 시도할 여지가 있다. 다만 학습한 모델을 AI HAT에서 구동하려면 변환이 필요하며 이 과정은 확인되지 않았다.

**D는 이번 학기 범위를 넘는다.** 데이터 수집과 라벨링이 전제된다.

### 2-5. 핵심 문제 2 — 손등·손바닥은 제공되지 않는다

MediaPipe가 제공하는 handedness는 왼손인지 오른손인지를 판정한 값이며, 손등이 보이는지 손바닥이 보이는지는 알려주지 않는다.

따라서 뒤집힘 판별은 다음 중 하나로 직접 구현해야 한다.

| 방법 | 내용 | 비고 |
|---|---|---|
| 랜드마크 기하 계산 | 손목·검지뿌리·새끼뿌리 세 점이 이루는 방향으로 판별 | 탑뷰에서 손을 세우면 세 점이 일직선에 가까워져 판정이 불안정해질 수 있음 |
| IMU 병용 | 글러브의 MPU-6050이 중력 방향으로 판별 | 카메라와 무관하게 값이 유지되며, 손이 가려져도 동작 |

**선택: IMU 병용을 기본으로 한다.** 카메라 판별은 손이 가려지거나 세워졌을 때 끊기지만, IMU는 중력 방향만 확인하면 되므로 조건에 영향을 받지 않는다. 이미 부품이 확보되어 있다는 점도 고려했다.

### 2-6. 핵심 문제 3 — handedness 반전

MediaPipe 문서는 handedness가 입력 이미지가 거울처럼 반전되었다고 가정하고 판정되며, 그렇지 않은 경우 애플리케이션에서 결과를 바꿔야 한다고 명시한다.

본 시스템은 셀피 카메라가 아닌 고정형 탑뷰 카메라를 사용하므로, 출력을 그대로 쓰면 좌우가 뒤바뀔 가능성이 있다. 실제 손과 대조해 반전 여부를 확인한 뒤 설정을 고정해야 한다.

## 3. STT

### 3-1. 요구 조건

본 시스템의 음성 인식은 자유로운 문장을 받아쓰는 것이 아니라, 정해진 소수의 명령을 판별하는 것이다.

| 항목 | 내용 | 출처 |
|---|---|---|
| 인식 대상 | 물체명 5종(컵·물병·휴대폰·책·마우스), 제어 명령(정지·목록), 선택 명령(왼쪽·오른쪽) | 팀 README |
| 어휘 규모 | 약 9개 | 위 항목 합산 |
| 발화 길이 | 짧은 명령. 최대 5초로 설정되어 있음 | `max_utterance_ms: 5000` |
| 실행 환경 | 라즈베리파이 5, 온디바이스 | 팀 README |
| 동시 부하 | 영상 추론과 CPU 공유 | AUDIO_SETUP 문서 |

이 조건 때문에 일반 받아쓰기 성능 지표(WER)를 그대로 적용하는 것은 적절하지 않다. 상세한 이유는 3-4에서 기술한다.

### 3-2. 후보 비교

| 후보 | 방식 | 온디바이스 | 한국어 | 비고 |
|---|---|---|---|---|
| whisper.cpp | Whisper의 C/C++ 재구현. 양자화 지원 | 가능 | 다국어 모델 지원 | 현재 팀 코드에 적용됨 |
| OpenAI Whisper (Python) | 원본 구현 | 가능하나 무거움 | 동일 | PyTorch 의존, 파이에 부적합 |
| 클라우드 STT API | 서버 전송 후 인식 | 불가 | 우수 | 과제 요구와 상충 |
| Moonshine | 엣지 기기 전용 경량 ASR | 가능 | 지원 | 한국어에서 Whisper 소형 모델보다 나은 수치 보고 |

**클라우드 API는 검토 대상에서 제외한다.** 본 과제는 설치 이후 클라우드를 호출하지 않는 온디바이스 동작을 전제로 하며, 사용자의 음성이 외부로 전송되지 않아야 한다는 요구도 있다.

**whisper.cpp를 기본으로 유지한다.** 팀 코드에 이미 적용되어 있고, C/C++ 구현에 양자화를 지원해 라즈베리파이급 장치에서 동작 가능한 형태다. Moonshine은 대안으로 기록해 둔다.

### 3-3. 모델 크기 — 조사된 수치

Moonshine 논문(arXiv 2509.02523)에 한국어 벤치마크 기준 Whisper 모델 크기별 성능이 제시되어 있다. 한국어 구간의 수치는 다음과 같다.

| 모델 | WER | CER |
|---|---|---|
| whisper-small | 30.31 / 22.61 | 15.19 / 11.09 |
| whisper-base | 59.54 / 46.03 | 35.54 / 22.79 |
| whisper-tiny | 100.9 / 91.89 | 72.46 / 61.18 |

현재 팀 기본 설정은 tiny(`ggml-tiny.bin`)다. 위 수치대로라면 일반 문장 받아쓰기에서는 사실상 사용이 어려운 수준이다.

한국어 성능이 낮은 배경도 확인된다. ENERZAi의 측정에 따르면 whisper-large-v3가 영어(LibriSpeech Other)에서 CER 3.91%였으나 한국어(KsponSpeech Eval-Other)에서는 11.13%로 크게 떨어졌다. Whisper의 학습 데이터 중 비영어 분량이 98개 언어에 나뉘어 있어 한국어 비중이 매우 작기 때문이라고 설명한다.

### 3-4. 이 수치를 그대로 적용할 수 없는 이유

위 WER은 임의의 문장을 정확히 받아쓰는 과제를 기준으로 측정된 값이다. 본 시스템의 과제는 다르다.

- 인식 후보가 9개로 고정되어 있다.
- 단어를 글자 단위로 정확히 맞힐 필요가 없고, 9개 중 어느 것인지만 판별하면 된다.
- 예를 들어 "컵"이 "컴"으로 인식되어도 후보 중 가장 가까운 것은 여전히 "컵"이다.

따라서 **평가 지표를 WER이 아니라 명령 인식 성공률로 정의한다.** 각 명령을 반복 발화했을 때 올바른 명령으로 매핑된 비율을 측정한다.

### 3-5. 설계

인식 정확도를 높이기 위해 세 층에서 접근한다.

```
[마이크] → ① VAD로 발화 구간 추출 → ② whisper.cpp STT → ③ 어휘 매핑 → [명령]
```

**① VAD (발화 구간 검출)**

현재 구현은 PCM 에너지 기준으로 발화를 판별한다. 팀 문서에도 훈련된 음성 분류기가 아닌 에너지 기준이며, 팬 소음이나 음악도 발화로 잡힐 수 있다고 기록되어 있다.

VAD 모델을 적용하면 말이 아닌 소리를 걸러낼 수 있다. Whisper는 무음이나 잡음이 입력되면 없는 문장을 생성하는 경향이 있으므로, 입력 단계에서 걸러내는 것이 오인식 감소에 직접 기여한다.

단, VAD는 WER 자체를 낮추지 않는다. 깨끗한 음성이 입력되었을 때의 인식 정확도는 변하지 않는다. 잡음 유입으로 인한 오동작을 줄이는 역할이다.

**② STT**

whisper.cpp로 한국어 인식을 수행한다. 모델 크기는 3-6에서 기술한다.

**③ 어휘 매핑**

STT 출력을 9개 후보 중 하나로 매핑한다. 방식 후보는 세 가지이며, 작동하는 층이 다르다.

| 방식 | 개입 시점 | 내용 | 구현 난이도 |
|---|---|---|---|
| 편집거리 | 인식 후 | 자모 단위로 후보와의 차이를 계산해 가장 가까운 것 선택 | 낮음 |
| 발음 유사도 | 인식 후 | 소리가 비슷한 자모(ㄱ/ㄲ, ㅐ/ㅔ 등)를 같게 취급 | 중 |
| Whisper 프롬프트 | 인식 전 | 후보 단어를 문맥으로 제공해 그쪽으로 기울게 함 | 낮음 |

**선택: 편집거리를 기본으로 구현한다.**

- 세 방식 중 구현이 가장 단순하고, 별도 라이브러리 없이 자모 분해만으로 가능하다.
- 인식 결과와 무관하게 항상 동작하므로 다른 방식의 가용 여부에 의존하지 않는다.
- 실측 후 부족하면 발음 유사도를 추가하는 방식으로 확장할 수 있다.

**상태에 따라 후보를 좁힌다.** 9개 명령이 항상 유효한 것은 아니다. 목표를 선택하기 전에는 물체명 5종과 '목록'만, 같은 물체가 여러 개일 때는 '왼쪽·오른쪽'만 유효하다. 현재 상태에서 가능한 명령만 후보로 두면 비교 대상이 2~6개로 줄어 오인식이 감소한다.

현재 팀 구현은 STT 결과를 허용 물체·정지 명령 사전으로 다시 검사하는 구조다. 이를 단순 일치에서 유사도 매칭으로 확장하는 것이 본 설계의 내용이다.

### 3-6. 모델 크기 선택

**tiny로 먼저 구현·측정하고, 결과가 기준에 미달하면 base로 상향한다.**

**tiny로 시작하는 이유**

- 3-4에서 기술했듯 어휘가 9개로 제한되므로, 일반 WER이 곧 명령 인식 실패를 뜻하지 않는다. 매핑 계층이 상당 부분을 보정할 것으로 예상된다.
- 가장 가볍고, 영상 추론과 CPU를 나눠 쓰는 조건에서 유리하다.
- 팀 코드의 현재 기본값이므로 추가 설치 없이 바로 측정에 들어갈 수 있다.
- 실측 전에 큰 모델로 확정하면 속도 문제를 뒤늦게 발견할 위험이 있다.

**전환 기준**

| 항목 | 기준 |
|---|---|
| 전환 조건 | 명령 인식 성공률이 90% 미만일 때 |
| 측정 시점 | 매핑 계층까지 적용한 뒤 측정. 매핑 없는 상태의 수치로 판단하지 않는다 |
| 결론 시점 | 8주차 프로토타입 시연 전 |

**순서가 중요하다.** tiny + 매핑을 먼저 측정하고, 그래도 미달일 때 base로 올린다. 매핑을 적용하지 않은 tiny의 수치만 보고 모델을 바꾸면 불필요하게 무거운 모델을 쓰게 된다.

**base로 상향할 경우의 전제**

- whisper.cpp의 양자화(q5, q8 등)를 적용해 메모리와 연산을 줄인다.
- 상주형 프로세스로 전환해야 한다. 현재 구현은 명령마다 자식 프로세스를 실행해 모델을 로드하는 구조이며, base는 tiny보다 로딩 시간이 길어 매번 로드하면 지연이 누적된다. 팀 문서에도 속도 검증 후 상주형으로 전환할 수 있다고 기록되어 있다.
- 영상 추론과의 CPU 사용을 다시 측정해야 한다.

단, whisper.cpp + base + 한국어 조합의 라즈베리파이 5 실측 성능은 확인하지 못했다. 양자화 시 동작 가능할 것으로 보이나 근거가 되는 벤치마크를 찾지 못했으며, 직접 측정해야 한다.

### 3-7. 검증 계획

현재 측정된 값은 없다.

| 항목 | 조건 | 측정 |
|---|---|---|
| 명령 인식 성공률 | 9개 명령을 각 20회 발화 | 올바른 명령으로 매핑된 비율 |
| 매핑 계층 효과 | 매핑 적용 전후 비교 | 성공률 차이 |
| 모델 크기 비교 | tiny vs base(양자화) | 성공률, 처리 시간 |
| 처리 지연 | 발화 종료부터 명령 확정까지 | 초 단위 |
| VAD 효과 | 에너지 기준 vs VAD 모델 | 오검출 횟수 |
| 잡음 내성 | 팬 소음, 배경 음악 조건 | 오검출 횟수 |
| 동시 부하 | 영상 추론 병행 시 | 처리 시간 변화 |
| 화자 변동 | 팀원 3인 발화 | 성공률 편차 |

## 4. TTS

### 4-1. 요구 조건

| 항목 | 내용 | 출처 |
|---|---|---|
| 출력 내용 | 주변 물체 목록, 목표 선택 확인, 손·목표 손실 안내, 근접 안내 | 팀 README |
| 문장 성격 | 대부분 고정 문장. 물체명만 바뀌는 형태 | 팀 README |
| 실행 환경 | 라즈베리파이 5, 온디바이스 | 팀 README |
| 사용자 | 시각장애인·저시력자 | 과제 대상 |

**출력 문장이 고정형이다.** "컵을 찾아 안내하겠습니다"처럼 틀이 정해져 있고 물체명만 치환된다. 팀 구현도 한 번 만든 안내 음성을 저장해두고 재사용하는 구조다.

### 4-2. 후보 비교

| 후보 | 방식 | 파이 구동 | 음질 | 비고 |
|---|---|---|---|---|
| eSpeak NG | 규칙 기반 포먼트 합성 | 매우 가벼움 | 기계음 | 현재 팀 코드에 적용됨 |
| Piper | VITS 기반 ONNX 신경망 | 파이 4·5에서 실시간 보고 | 자연스러움 | 모델 60~150MB(medium) |
| Kokoro | StyleTTS2 계열, 82M 파라미터 | 파이 실시간 벤치마크 미확인 | 자연스러움 | 한국어 지원 |
| 클라우드 TTS | 서버 합성 | 불가 | 우수 | 온디바이스 요구와 상충 |

조사된 평가는 다음과 같다.

- eSpeak NG는 가장 가볍고 지연이 낮으며 100개 이상 언어를 지원하지만 기계음에 가깝다. 알림이나 스크린리더처럼 음질보다 지연이 중요한 용도에 적합하다고 평가된다.
- Kokoro는 더 자연스러운 음질이나 파이에서의 실시간 벤치마크가 문서화되어 있지 않다.

팀 문서에도 eSpeak NG의 한국어 발음이 자연스러운 음성 모델과 차이가 있으므로, 대상 물체 이름이 사용자에게 명확하게 들리는지 확인하고 필요하면 교체하라고 기록되어 있다.

### 4-3. 설계

**고정 문장은 미리 합성해 WAV로 보관하고, 재생만 수행한다.**

이 구조에서는 합성 엔진의 실시간 성능이 문제되지 않는다. 개발 PC에서 여유 있게 합성해 파이에 파일로 넣어두면, 실행 중에는 WAV 재생만 하므로 CPU 부담이 거의 없다.

| 구분 | 처리 방식 | 엔진 요구 |
|---|---|---|
| 고정 안내 문장 | 사전 합성 후 WAV 재생 | 실시간 성능 불필요. 음질만 고려 |
| 물체명 치환 문장 | 물체명이 5종으로 한정되므로 조합 수가 적음. 사전 합성 가능 | 동일 |
| 예외적 즉석 문장 | 실시간 합성 | 가벼운 엔진 필요 |

팀 구현은 이미 고정 안내 WAV를 저장해두고 같은 문장이 나오면 재사용한다. 다만 이는 실행 중에 만든 음성을 다시 쓰는 방식이다. 본 설계는 이를 개발 단계에서 미리 만들어 두는 방식으로 확장하는 것이며, 합성 엔진을 파이 성능과 무관하게 고를 수 있다는 점이 다르다.

### 4-4. 엔진 선택

**eSpeak NG를 유지하되, 청취 평가 결과에 따라 사전 합성 부분만 Piper로 교체한다.**

본 시스템의 음성 출력은 미리 만들어두는 고정 문장과 즉석에서 합성하는 예외 문장으로 나뉜다. 두 구간에 서로 다른 엔진을 쓸 수 있다.

| 구간 | 엔진 | 이유 |
|---|---|---|
| 사전 합성 | Piper (평가 후) | 개발 PC에서 생성하므로 무거워도 무방. 음질만 고려 |
| 즉석 합성 | eSpeak NG | 파이에서 바로 실행되어야 하므로 가벼워야 함 |

선택 근거는 다음과 같다.

- eSpeak NG는 이미 팀 코드에 적용되어 있고 설치도 가볍다. 즉석 합성이 필요한 경우의 대비책으로 유지할 가치가 있다.
- 4-3의 구조에서는 고정 문장의 음질만 개선하면 되므로, 무거운 엔진을 써도 실행 중 부담이 없다.
- Piper는 파이 4에서도 실시간 동작이 보고되므로, 사전 합성이 아니라 실시간으로 돌려야 하는 상황이 와도 대응할 수 있다.
- Kokoro는 파이 실시간 성능이 확인되지 않아 후보로만 둔다.

**판단 기준은 음질 점수가 아니라 알아듣는가이다.** 물체명 5종을 들려주고 정확히 구분되는지 확인한다.

### 4-5. 재생 속도에 관한 검토

시각장애인 사용자가 화면 낭독 음성을 2~3배속으로 듣는 경우가 많다는 지적이 있었다. 배속 재생 시 음질이 손상되는 문제를 개선하는 방향도 검토 대상으로 거론되었다.

다만 본 시스템의 안내 문장은 짧고 종류가 한정되어 있어, 긴 문서를 빠르게 읽는 상황과는 조건이 다르다. 재생 속도 조절 기능 자체는 넣되, 배속 시 음질 보정은 후속 과제로 둔다.

eSpeak NG는 `-s` 옵션으로 속도를 조절할 수 있으며, 팀 문서의 예시에도 `-s 155`가 사용되어 있다. 사전 합성 방식을 쓰는 경우 속도별로 여러 벌을 미리 만들어 두는 방법도 가능하다.

### 4-6. 스피커 소리의 재입력 방지

현재 구현은 TTS 재생 중과 종료 직후에 마이크 입력을 버린다. 팀 문서에 `echo_cooldown_ms: 300`으로 잔향 구간이 설정되어 있다.

이 방식의 한계도 문서에 기록되어 있다. 안내 중에는 사용자의 음성 요청과 정지 명령도 받을 수 없다. 안내 도중 끼어드는 기능은 반향 제거 등 추가 처리가 필요한 후속 항목이다.

본 설계에서는 이 구조를 유지하되, 안내 문장을 짧게 유지해 차단 구간을 줄인다. 사전 합성 방식은 합성 지연이 없으므로 차단 구간이 재생 시간만큼으로 줄어든다는 부수적 이점이 있다.

### 4-7. 검증 계획

현재 측정된 값은 없다.

| 항목 | 조건 | 측정 |
|---|---|---|
| 물체명 청취 구분 | 물체명 5종을 무작위 재생 | 정확히 들은 비율 |
| 엔진 비교 | eSpeak NG vs Piper | 위 비율 차이 |
| 합성·재생 지연 | 사전 합성 / 즉석 합성 | 요청부터 재생 시작까지 |
| 배속 명료도 | 1.0 / 1.5 / 2.0배속 | 구분 비율 |
| 에코 차단 | TTS 재생 중 발화 | 오인식 발생 여부 |
| 저장 용량 | 사전 합성 파일 전체 | MB |

## 5. 프론트

### 5-1. 범위

파트 정의에 따라 상태 표시로 범위를 한정한다. 즉 지금 손이 어떻게 인식되고 있고 어느 물체가 인식되고 있는지를 보여주는 화면이다. 목표 물체를 고르는 입력은 음성(STT)과 개발용 키보드 입력이 담당하므로 본 파트에 포함하지 않는다.

사용자가 시각장애인·저시력자이므로 **이 화면은 사용자용이 아니다.** 보는 대상은 두 부류다.

| 대상 | 용도 |
|---|---|
| 개발자 | 인식이 제대로 되는지, 명령이 올바르게 생성되는지 확인 |
| 시연 관람객 | 착용자가 아닌 사람이 진행 상황을 이해 |

부스 시연에서는 관람객이 직접 장갑을 착용해 체험하지만, 진동은 착용자 한 명만 느낄 수 있다. 대기 중인 관람객이 진행 상황을 볼 수 있도록, 그리고 체험자가 체험 후 자신의 동작을 확인할 수 있도록 화면이 필요하다.

### 5-2. 현재 구현과 제약

팀 코드에는 두 가지 표시 수단이 이미 있다.

| 수단 | 내용 | 제약 |
|---|---|---|
| OpenCV 미리보기 (`show_preview`) | 물체 상자와 손바닥 대표점 표시 | 파이에 모니터가 연결되어 있어야 한다. SSH 환경에서는 `false` 유지 |
| 터미널 출력 (`--console`) | `state`, `direction`, `proximity`, `levels` 출력 | 관람객에게 보여주기 부적합 |

또한 9월 18일 설계 문서에 FastAPI와 WebSocket이 후보로 언급되어 있다.

**미리보기는 원격 접속 시 볼 수 없고, 터미널 출력은 시연에 쓸 수 없다.** 이 두 제약이 본 파트의 출발점이다.

### 5-3. 표시할 내용

파트 정의의 두 항목과 팀 코드가 이미 산출하는 값을 결합한다.

| 구분 | 항목 | 출처 |
|---|---|---|
| 핸드 인식 상태 | 손 검출 여부 | MediaPipe |
| | 손 위치 | MediaPipe |
| | 손등·손바닥 | MPU-6050 |
| 물체 인식 상태 | 인식된 물체 목록과 위치 | YOLO |
| | 목표로 선택된 물체 | `controller.py` |
| 안내 상태 | `state` (탐색·도달·중단 등) | 팀 코드 |
| | `direction` | 팀 코드 |
| | `proximity` | 팀 코드 |
| | `levels` (손가락별 진동 세기 5개) | 팀 코드 |

네 상태값은 팀 README의 `--console` 실행 안내에 확인 대상으로 명시되어 있다. 다만 각 값의 구체적인 형식은 코드를 확인해야 하며, 위 표의 상태 구분은 9월 18일 설계 문서의 상태 목록에 근거한 것이다.

**`levels` 표시가 유용하다.** 어느 손가락이 어느 세기로 울리고 있는지 화면에 보이면, 진동을 느끼지 못하는 사람도 시스템의 동작을 이해할 수 있다. 개발 중에도 명령은 전송되었는데 모터가 동작하지 않는 경우와 명령 자체가 생성되지 않은 경우를 구분할 수 있다.

### 5-4. 표시 방식 후보

| 방식 | 프로그램 실행 위치 | 화면 위치 | 장점 | 단점 |
|---|---|---|---|---|
| 터미널 출력 | 파이 | SSH 접속한 노트북 | 이미 구현됨. 부하 없음 | 시연 부적합 |
| OpenCV 창 | 파이 | 파이에 연결된 모니터 | 이미 구현됨. 영상 위에 직접 표시 | 원격에서 볼 수 없음 |
| 웹 | 파이 (서버) | 노트북·외부 화면 브라우저 | 모니터 불필요. 시연 시 큰 화면 연결 용이 | 새로 구현해야 함 |

**웹 방식을 목표로 하되 단계적으로 구현한다.**

선택 근거는 다음과 같다.

- 파이에 모니터를 연결하지 않아도 되므로, 현재 팀의 개발 방식(원격 접속)과 맞는다.
- 시연 시 외부 화면이나 프로젝터에 연결하기 쉽다.
- 여러 명이 동시에 볼 수 있다.

**구현 기술: FastAPI와 WebSocket**

FastAPI로 웹 서버를 구성하고, 상태값 전송은 WebSocket으로 처리한다.

| 기술 | 역할 |
|---|---|
| FastAPI | 파이썬 웹 서버. 브라우저가 파이에 접속할 수 있게 한다 |
| WebSocket | 연결을 유지한 채 서버가 데이터를 보내는 통신 방식 |

WebSocket을 쓰는 이유는 상태값이 계속 갱신되기 때문이다. 일반 HTTP 요청은 브라우저가 매번 물어봐야 하므로 초당 여러 번 갱신하려면 그만큼 요청이 반복된다. WebSocket은 한 번 연결하면 서버가 변경 사항을 밀어줄 수 있어 주기적 전송에 적합하다.

FastAPI에 WebSocket 기능이 포함되어 있어 별도 라이브러리가 필요하지 않다. 또한 기존 코드가 파이썬이므로 언어가 같다.

9월 18일 설계 문서에 두 기술이 후보로 언급되어 있으나 필수 구현 조건으로 확정하지는 않았다. 본 파트에서 위와 같이 선택한다.

### 5-5. 전송 내용

**영상 전체를 계속 전송하면 대역폭과 지연이 문제가 된다.** 따라서 전송 내용을 나눈다.

| 구분 | 전송 방식 | 주기 |
|---|---|---|
| 상태값 (`state`, `direction`, `proximity`, `levels`) | 텍스트·숫자 | 초당 5~10회 |
| 물체·손 좌표 | 좌표값 | 동일 |
| 영상 | 낮은 화질, 낮은 프레임률. 필요할 때만 | 초당 1~5회 또는 요청 시 |

상태값과 좌표만 보내면 데이터량이 매우 작다. 브라우저에서 좌표를 받아 도형으로 그리면 영상 없이도 위치 관계를 표현할 수 있다. 영상은 물체 인식이 제대로 되는지 확인할 때만 필요하므로 별도 옵션으로 둔다.

### 5-6. 구현 단계

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 1 | 터미널 출력 정리 | 현재 상태를 한눈에 읽을 수 있는 형식 |
| 2 | 상태값 웹 전송 | 브라우저에서 `state`·`direction`·`levels` 확인 |
| 3 | 좌표 시각화 | 물체와 손의 위치를 도형으로 표현 |
| 4 | 영상 표시 (옵션) | 낮은 화질로 카메라 화면 확인 |
| 5 | 시연용 화면 정리 | 관람객이 이해할 수 있는 배치 |

**1단계부터 순서대로 진행하며, 앞 단계가 동작하면 다음으로 넘어간다.** 웹 구현부터 시작하면 상태를 확인할 수단 없이 개발하게 되므로, 터미널 출력을 먼저 정리해 개발 중에 쓸 수 있는 형태로 만든다. 여기서 정한 표시 항목과 형식이 이후 웹 화면의 기준이 된다.

## 6. 구현 구조

### 6-1. 모듈별 담당

팀 코드의 기존 모듈 기준으로 정리한다.

| 모듈 | 역할 | 본 파트 관련 |
|---|---|---|
| `vision.py` | 카메라, 물체 검출, 손 추적 | 손 추적 부분 담당 |
| `audio.py` | 녹음, 발화 추출, STT, TTS | 전체 담당 |
| `controller.py` | 목표 선택·추적, 방향·근접도, 상태 전환 | 상태값을 프론트로 전달 |
| `runtime.py` | 병행 실행, 오류·종료 처리 | 프론트 작업 추가 |
| `ble_link.py`, `protocol.py` | BLE 연결, 패킷 | 해당 없음 |
| (신규) 프론트 모듈 | 상태 전송·표시 | 신규 작성 |

`vision.py`는 물체 검출과 손 추적이 한 파일에 있으므로, **물체 인식 파트와 같은 파일을 수정하게 된다.** 팀 규칙에 따라 사전에 공유한다.

### 6-2. 데이터 흐름

**손 인식**

```
카메라 프레임 → MediaPipe → 손 랜드마크 21개 → 손 기준점 좌표
                                              → controller.py
```

손 기준점은 손목과 손가락 뿌리 관절의 평균으로 정의되어 있다. 손등·손바닥 판별은 카메라가 아니라 글러브의 MPU-6050이 담당하므로, 본 파트는 위치만 산출한다.

**음성 입력**

```
마이크 → VAD로 발화 구간 추출 → whisper.cpp → 텍스트
       → 편집거리 매핑 → 명령 확정 → controller.py
```

매핑 시 현재 상태에서 유효한 명령만 후보로 둔다.

**음성 출력**

```
controller.py → 안내 요청 → 사전 합성 WAV 있으면 재생
                          → 없으면 즉석 합성 후 재생
```

**프론트**

```
controller.py → 상태값·좌표 → 프론트 모듈 → 브라우저
카메라 프레임 → (옵션) 저화질 변환 → 프론트 모듈 → 브라우저
```

### 6-3. 실행 원칙

팀 설계 문서의 원칙을 따른다.

- 영상 추론, 음성 처리, BLE를 독립된 작업으로 나눈다.
- STT나 TTS 처리 중에도 영상과 BLE 동작을 유지한다.
- 안내 주기, 영상 처리 주기, BLE 전송 주기를 분리한다.

여기에 본 파트의 원칙을 추가한다.

- **프론트는 부가 기능이며, 실패해도 본체 동작을 막지 않는다.** 브라우저 접속이 없거나 전송에 실패해도 안내는 계속되어야 한다.
- **TTS 재생 중 마이크 입력을 버리는 구조를 유지하되, 안내 문장을 짧게 유지해 차단 구간을 줄인다.** (4-6 참조)

### 6-4. 구현 순서

| 순서 | 작업 | 선행 조건 | 완료 기준 |
|---|---|---|---|
| 1 | 맨손 인식 확인 | 카메라·AI HAT 수령 | 탑뷰에서 손 좌표 산출 |
| 2 | 장갑 인식 측정 | 장갑 시제품 | 착용 상태 인식률 확보 |
| 3 | 검출기 보강 (필요 시) | 2의 결과 | 인식률 개선 확인 |
| 4 | STT 기본 동작 | 마이크 수령 | 명령이 텍스트로 변환됨 |
| 5 | 어휘 매핑 구현 | 4 | 명령 인식 성공률 측정 |
| 6 | TTS 사전 합성 | 스피커 수령 | 고정 문장 재생 |
| 7 | 프론트 상태 전송 | 1·4 | 브라우저에서 상태 확인 |
| 8 | 프론트 시각화 | 7 | 위치 관계 표현 |

**장갑 인식률이 이후 작업의 분기점이 된다.** 맨손 수준에 근접하면 3번을 생략할 수 있고, 크게 떨어지면 검출기 보강이나 파인튜닝이 필요하다. 장갑 시제품이 나오는 대로 먼저 측정한다.

### 6-5. 다른 파트와의 접점

| 파트 | 접점 | 확인 필요 사항 |
|---|---|---|
| 물체 인식 | `vision.py` 공유, 동일 프레임 사용 | 파일 수정 시 사전 공유. 좌표계 일치 확인 |
| 글러브 | `controller.py`가 생성한 명령을 BLE로 전달 | 손등·손바닥 판별을 MPU에서 받는 경로 |
| 전체 | AI HAT 자원 공유 | 손 검출기를 추가할 경우 YOLO와의 동시 구동 가능 여부 |

## 7. 추가로 필요한 부품

| 부품 | 용도 | 비고 |
|---|---|---|
| USB 마이크 | STT 입력 | 현재 목록에 없음. 파이와 카메라 모듈 모두 마이크를 내장하지 않음 |
| 스피커 | TTS 출력 | 현재 목록에 없음. 파이 5는 3.5mm 오디오 출력이 없어 USB 또는 I2S 연결 필요 |

두 부품이 확보되기 전까지는 녹음 파일을 이용해 인식률과 매핑 성능을 측정한다. 실시간 발화 구간 검출, 잡음 환경 대응, 스피커 소리의 재입력 방지는 부품 수령 후 검증한다.

**스피커는 카메라 측에 고정하는 것을 전제로 한다.** 글러브에 부착하면 손 움직임에 따라 소리 위치가 바뀌고 배터리 부담도 늘어난다.

## 8. 미해결 문제

### 팀 확인이 필요한 사항

- **프론트의 범위.** 본 문서는 파트 정의에 따라 상태 표시로 한정했으나, 화면에서 목표 물체를 선택하는 입력까지 포함하는지 확인이 필요하다.
- **물체명의 표현 변형을 어디까지 허용할지.** 머그컵/컵, 스마트폰/휴대폰 등을 같은 명령으로 처리할지 정해야 한다.

### 확인이 필요한 기술 사항

- **Piper의 한국어 음성 가용 여부.** 자료가 엇갈린다. 한쪽은 음성 목록에 한국어가 포함된다고 하고, 다른 쪽은 쓸 만한 한국어 음성이 없다고 기술한다. 실제 음성을 확보해 들어본 뒤 판단해야 한다.
- **whisper.cpp 실행 옵션.** `--prompt` 계열 옵션이 v1.9.4에 실제로 노출되는지 `whisper-cli --help`로 확인해야 한다. 편집거리 매핑만으로 목표 인식률에 도달하면 적용하지 않는다.
- **MC-hands-1M의 라이선스와 구동 가능 여부.** 파인튜닝을 진행할 경우 먼저 확인해야 한다.

### 아직 정하지 못한 사항

- **사전 합성의 단위.** 문장 전체를 미리 만들지, 문장 조각을 이어 붙일지 정하지 않았다. 후자는 파일 수가 적지만 이어 붙인 부분이 어색해질 수 있다. 조합 수와 저장 용량도 산정하지 않았다.

### 부품 수령 후 판단할 사항

- **장갑에 모터와 PCB가 부착된 상태의 인식 가능 여부.** 문헌의 장갑 사례는 모두 매끈한 의료용·작업용 장갑이며, 부착물이 있는 경우의 보고는 찾지 못했다.
- **손 검출기 추가 시 AI HAT 동시 구동 가능 여부.** B안을 적용하면 물체 인식용 YOLO와 함께 두 모델이 AI HAT에서 돌아간다. 둘을 함께 올릴 수 있는지, 처리 시간이 얼마나 늘어나는지 확인해야 한다.
- **음성 계열 실시간 검증.** USB 마이크와 스피커가 확보되면 실시간 발화 구간 검출, 잡음 환경 대응, 스피커 소리가 마이크로 되돌아오는 문제를 측정한다. 확보 전까지는 녹음 파일로 인식률과 매핑 성능을 먼저 측정한다.

### 후속 과제로 둔 사항

- 안내 도중 음성으로 끼어드는 기능. 반향 제거 등 추가 처리가 필요하다.
- 배속 재생 시의 음질 개선.

# 라즈베리파이–ESP32 실기기 연동 오류 해결 회고

- 작성일: 2026-10-29
- 작성자: DH
- 대상: 카메라 물체·손 인식, BLE 송신, ESP32-C3 진동 장갑
- 상태: **최종 수정 후 사용자가 실기기 동작 성공을 확인함**
- 범위: 전날부터 이어진 BLE 문제를 포함해, 이번 연동을 완료하는 과정에서 겪은 오류와 해결 내용을 정리한다.

## 1. 오늘의 결과

물체가 손에 가려져 검출되지 않는 LOCKED 상태에서도 마지막 목표 위치로 진동 안내를 이어가고, 손바닥 중심과 목표 중심이 가까워지면 획득으로 판정하도록 수정했다. 안내는 mode 3을 기본으로 사용한다.

최종 동작은 다음과 같다.

1. 프로그램 실행 → 시동어 → 목표 물체 선택.
2. mode 3으로 방향과 근접도에 따른 진동 안내.
3. 물체가 가려지면 마지막 목표 위치를 잠금 상태로 유지.
4. **손바닥 중심과 목표 중심이 50px 이내에서 5개 연속 유효 프레임 동안 유지되면 획득 판정.**
5. **다섯 진동 모터가 최대 PWM 255로 350ms 진동 → 200ms 정지 → 350ms 진동.**
6. 획득 음성 안내 후 시동어 대기 상태로 복귀.

이 획득 판정은 영상의 2D 좌표를 이용한 규칙이다. 실제로 물체를 쥐었는지, 손과 물체의 깊이가 같은지를 별도 센서로 확인한 것은 아니다.

## 2. 발생한 문제와 원인·해결

### 2.1. 손을 돌리면 BLE 진동 안내가 끊김

**증상**

손을 목표 물체 쪽으로 돌리는 순간 진동 안내가 중단됐다. Pi에서는 명령 쓰기 응답 시간 초과가 발생했고, ESP에서는 다음 로그가 확인됐다.

```text
flags=03 seq=167 ... on=1
flags=05 seq=168 ... on=0
flags=00 seq=0   ... on=0
```

Pi의 대응 오류는 다음과 같았다.

```text
명령 쓰기 seq=168 ... 응답 0.301초 초과 (제한 0.3초)
```

**무엇이 좋지 않았나**

ESP는 이미 `seq=168`을 수락했는데, Pi는 GATT 쓰기 완료 응답을 0.3초 안에 받지 못했다는 이유로 실패 처리했다. 명령 전달 여부와 응답 완료 시점을 같은 짧은 제한으로 판단한 것이 실제 환경에 맞지 않았다.

또한 `flags=05`는 연결 상태에서 TTL이 만료됐다는 뜻이고, 이후 `flags=00 seq=0`은 연결 종료 처리로도 발생한다. 이 로그만으로 ESP가 재부팅됐다고 단정하면 원인을 잘못 좁힐 수 있었다.

**해결**

- 안내 명령의 GATT 응답 제한을 **0.3초에서 1초로 조정**했다.
- 응답 대기 시간과 ESP의 모터 TTL을 분리했다.
- 늦은 응답은 지연 로그를 남기되, 제한 안에서 완료되면 연결을 유지한다.
- 실제 통신 실패가 나면 진동을 멈추고 영상·음성은 유지하며, `reconnect` 후 `resume`으로 재개한다.

**결과와 남은 불확실성**

사용자가 응답 제한 변경 후 진동 끊김이 사라졌다고 확인했다. 다만 보드를 손과 함께 회전할 때 지연이 생긴 물리적 원인까지 측정한 것은 아니다. 안테나·전원 문제로 확정하지 않는다.

### 2.2. 손이 물체를 가리면 진동과 획득 판정이 함께 멈춤

**증상**

손가락이나 손이 목표 박스에 겹치면서 물체 검출이 사라졌다. 화면에는 잠금 박스가 남아 있어도 실제 안내는 멈췄고, 손 중심이 목표 중심에 도달해도 획득되지 않았다.

**원인**

기존 코드는 현재 프레임에서 목표가 검출된 `found_target`이 있어야 BLE 안내와 획득 판정을 진행했다. 화면에 남긴 `locked_target_box`는 실제 제어에 충분히 연결되지 않았다. 목표 미검출이 45프레임을 넘으면 잠금도 해제했다.

즉, **화면에 보이는 잠금 상태와 제어에 사용하는 상태가 달랐다.** 물체를 찾으려면 손을 가까이 가져가야 하는데, 가까이 가서 물체를 가리는 순간 제어 조건이 깨지는 구조였다.

**해결**

- 목표가 보이지 않아도 마지막 `locked_target_box`와 중심을 유지한다.
- 45프레임 미검출만으로 목표를 자동 해제하던 조건을 제거했다.
- 현재 손 좌표와 잠금 목표 좌표로 안내와 획득 판정을 계속한다.
- 마지막 물체 관측 시각은 `target_seen_at`으로 별도 보존한다. 이전 물체 좌표를 새로 검출한 것처럼 시각을 갱신하지 않는다.
- 손 좌표에는 현재 프레임 유효성·신선도 검사를 유지한다. 손까지 상실하면 정지한다.
- 화면에 `LOCKED: 마지막 목표 위치로 안내 계속`을 표시한다.

**한계**

가려진 물체가 마지막 위치에 있다는 가정이다. 가려진 동안 물체 자체가 움직였는지는 알 수 없다. 위치를 다시 선택하려면 취소 후 목표를 재선택해야 한다.

### 2.3. 우리가 원하는 획득 기준과 구현 기준이 달랐음

**문제의 변화**

처음에는 중지 뿌리 관절 9와 물체 중심 사이의 거리로 완료를 판단했다. 이후 손가락 끝이 물체 박스 안쪽에 0.4초 머무르면 도달하는 방식으로 변경했지만, 최종 요구인 **손바닥 중심과 목표 중심의 겹침**과는 달랐다.

손가락 끝이 박스에 들어간 것, 손바닥이 목표에 도달한 것, 실제로 잡은 것을 구분하지 않으면 완료 시점이 사용자의 기대와 어긋났다.

**해결**

- 손바닥 중심을 랜드마크 **0, 5, 9, 13, 17의 평균 좌표**로 통일했다.
- 실제 영상의 가로·세로 크기를 적용해 중심 사이 픽셀 거리를 계산한다.
- 기본값을 **50px 이내, 5개 연속 유효 프레임**으로 설정했다.
- 거리 이탈, 손 상실, 무효·중복·오래된 프레임, 새 목표는 유지 카운터를 초기화한다.
- `--reach-px`와 `--reach-frames`로 기준을 조절할 수 있게 했다.
- 화면과 로그에 손바닥 중심, 중심 간 거리, 현재 유지 프레임 수를 표시했다.

```text
Palm-target: 현재 거리(px) | Grab: 현재 프레임/필요 프레임
```

### 2.4. 손을 옆으로 돌리면 획득까지 막힐 수 있었음

**원인**

획득 판정에 방향 안내용 좌표 검증을 재사용하면, 손바닥/손등 방향 축이 불확실하다는 이유로 손바닥 중심 자체도 사용하지 못했다. 방향 선택에 필요한 조건과 중심 겹침에 필요한 조건이 서로 달랐다.

**해결**

획득용 손바닥 관측 검증을 방향 축 검증과 분리했다. 현재의 유효한 손 좌표가 있으면, 방향 축이 불확실해도 손바닥 중심으로 획득을 검사한다. 무효 좌표·완전히 붕괴한 손 좌표·오래된 관측은 계속 거부한다.

### 2.5. mode 3 근접 진동이 한 번만 울리고 끝남

**증상과 원인**

기존 mode 3의 near는 중지가 두 번 울리는 일회성 알림이었다. 따라서 통신이 정상이고 획득 전이어도 근접 알림이 끝나면 조용해졌다. 사용자는 이를 연결 끊김이나 안내 중단으로 느낄 수 있었다.

**해결**

- 기본 안내 모드를 **mode 3**으로 변경했다.
- near는 중지 **200ms ON / 200ms OFF 반복**으로 바꿨다.
- far와 middle도 기존 주기로 반복하며, 획득 전까지 안내를 이어간다.
- 방향 전환 안정화 투표 중에는 현재 손·잠금 좌표가 유효한 동안 직전 확정 안내를 잠깐 유지해 불필요한 STOP을 줄였다.
- 손 상실·무효 좌표·취소·종료·통신 실패에 따른 정지는 유지했다.

여기서 지속 안내는 패턴의 반복을 뜻한다. 패턴에 포함된 OFF 구간까지 없애 모든 모터를 계속 켠다는 뜻은 아니다.

### 2.6. 획득 알림이 없거나 짧고, 일반 안내와 구분하기 어려움

**무엇이 어려웠나**

일반 안내를 멈추는 것만으로는 완료인지 관측 상실인지 알기 어려웠다. 반대로 완료 명령을 주기적으로 갱신할 때마다 패턴을 처음부터 실행하면 진동이 끝나지 않을 수 있었다. 시동어 대기로 돌아가는 일반 idle 메시지가 완료 패턴을 중간에 끊는 문제도 고려해야 했다.

**해결**

- 일반 안내와 별도의 획득 이벤트를 만들었다.
- 같은 목표에 대해 획득 이벤트를 한 번만 생성하고, 이벤트 ID로 중복 실행을 막는다.
- 전체 모터 **PWM 255**로 **350ms ON → 200ms OFF → 350ms ON**, 총 900ms 한 회 후 OFF한다.
- `--duties`로 일반 안내를 낮춰도 획득 알림은 최대값을 사용한다.
- 일반 idle과 명시적 STOP을 구분한다. 시동어 대기 복귀는 완료 알림을 자르지 않고, 취소·stop·연결 종료는 즉시 끈다.
- 일반 안내 TTL은 **500ms**, 획득 이벤트 TTL은 **1000ms**로 설정했다.
- Pi는 최대 1.9초의 유한한 전달 창에서 같은 이벤트를 갱신하지만, ESP 출력 패턴은 최초 수신부터 900ms 한 회뿐이다.

진동 시간은 논의 과정에서 변경됐으며, 최종 요청은 **350ms씩 두 번**이다. 1.5초 알림은 최종 적용값이 아니다.

### 2.7. 업로드했는데도 구버전 펌웨어라고 나옴

**원인**

개발용 Git 작업 폴더와 실제 Arduino에서 열던 바탕화면 프로젝트의 경로가 달랐다. `.ino` 파일은 사실상 같아 보여도, 같은 폴더의 `pattern_protocol.h`가 구버전이면 새 패턴 엔진이 들어가지 않는다.

실제로 바탕화면 프로젝트의 헤더에서는 상태 byte 15가 `0`이었고, 개발 폴더의 초기 확장판은 `3`이었다. 최종 수정판은 **7(0x07)**이다. 별도 업로드 폴더를 추가로 만드는 대응도 사용 경로를 더 헷갈리게 했다.

**해결**

- 사용자가 지정한 **기존 `esp32_device/ble_final` 경로**에 최신 스케치와 헤더를 반영했다.
- 기존 실기기 설정인 `DRY_RUN=false`를 유지했다.
- 헤더 전체가 최신 소스와 같은지 해시로 확인했다.
- Pi는 초기 STOP 후 capability를 검사한다. 숫자만 바꿔 구버전 검사를 우회하지 않는다.
- 시작 로그에 기능 정보를 넣어 업로드된 기능을 바로 확인하도록 했다.

```text
caps=07 | acquire=350,200,350ms | near=repeat
```

사용 경로:

```text
03. 김가네 캡스톤 디자인/
  esp32_device/ble_final/firmware/ble_final_receiver/
    ble_final_receiver.ino
    pattern_protocol.h
```

**교훈:** Git에 push·merge된 상태와 실제 장치에 업로드된 파일은 별도로 확인해야 한다. 펌웨어는 `.ino` 하나가 아니라 같은 폴더의 헤더까지 하나의 배포 단위다.

### 2.8. Arduino 빌드의 마지막 링크 단계에서 실패

**증상과 원인**

소스 컴파일 이후 ELF 파일을 만드는 단계에서 출력 파일을 열 수 없다는 오류가 발생했다. 오류 메시지에서 한글 경로가 깨져 있었고, Windows 빌드 도구가 한글 출력 경로를 제대로 처리하지 못한 경우였다.

**해결**

프로젝트 이름이나 소스를 불필요하게 바꾸지 않고, 빌드 출력 위치를 영문 임시 경로로 변경해 전체 빌드를 완료했다. 이 오류는 BLE 로직 문제와 분리해 처리했다.

## 3. 특히 어려웠던 점

### 서로 다른 계층에서 같은 증상이 발생했다

진동이 멈췄다는 현상 하나에 BLE 응답 시간 초과, ESP TTL 만료, 영상 미검출 STOP, 방향 검증 실패, 일회성 근접 패턴 종료가 모두 관련될 수 있었다. 진동 유무만 보고 원인을 단정하기 어려웠다.

Pi의 오류 시각·sequence와 ESP의 sequence·flags·논리 duty를 함께 확인하면서 통신 문제와 판단 로직 문제를 나눴다.

### 정지해야 할 때와 계속 안내해야 할 때를 구분해야 했다

모든 미검출을 즉시 정지로 처리하면 물체를 가리는 실제 획득 과정이 실패했다. 반대로 과거 손 좌표까지 무조건 유지하면 현재 손 위치와 다른 안내를 할 수 있었다.

따라서 **물체는 명시적으로 잠근 마지막 위치를 유지하고, 손은 현재의 유효한 관측을 사용**하도록 역할을 나눴다. 이 구분이 가림 문제를 해결한 핵심이었다.

### 방향 안내와 획득 기준을 따로 설계해야 했다

방향 안내에는 손의 좌표축과 자세가 필요하지만, 중심 겹침 판정에는 같은 조건이 모두 필요하지 않았다. 공통 검증을 그대로 재사용하는 것이 오히려 획득을 막을 수 있어 두 판단을 분리했다.

### 두 장치의 코드·규격·실제 업로드 상태를 맞춰야 했다

Pi의 새 송신 코드만으로는 ESP의 일회성 패턴이나 지원 기능을 바꿀 수 없다. 두 코드를 함께 갱신하고, capability와 시작 로그로 실행 중인 펌웨어를 확인하는 절차가 필요했다.

| Python 정적 검사 | ruff 통과 |
| Arduino 전체 빌드 | ESP32-C3, Arduino-ESP32 3.3.11, NimBLE-Arduino 2.5.1, USB CDC 설정 성공 |
| 최종 빌드 크기 | 플래시 585,837바이트(44%), RAM 23,760바이트(7%) |
| 실기기 확인 | 최종 코드 적용 후 사용자가 “성공했어!”라고 동작 성공을 보고함 |

주요 검사는 가림 중 획득, 장시간 잠금 유지, 손 상실 정지, 방향 축이 불확실한 손의 중심 판정, 반복 near 진동, 350/550/900ms 출력 경계, TTL·STOP·이벤트 중복 억제, 실제 detector 루프와 Pi 내부 UDP 송신 경로를 포함했다.

PC 시험과 실기기 확인은 구분한다. 성공 보고로 최종 연동 동작은 확인됐지만, 장시간 성공률·오획득률·무선 지연 분포·실제 출력 타이밍·전류와 전압은 이번 기록에서 정량 측정하지 않았다.

## 5. 다음에 개선할 점

- 업로드 전 실제 파일 경로와 헤더 버전, `DRY_RUN` 설정을 한 번에 확인할 수 있게 한다.
- 영상 로그의 `LOCKED`, 손 관측 유효성, 중심 거리, 유지 프레임, BLE 상태를 같은 시험 기록에 남긴다.
- 물체 종류와 가림 정도를 바꿔 50px/5프레임 기준을 평가한다. 해상도가 바뀌면 고정 px 기준도 다시 확인한다.
- 가려진 동안 물체가 이동하는 경우를 별도로 시험하고, 필요하면 물체 추적이나 사용자 재선택 절차를 개선한다.
- 장갑을 착용한 상태에서 방향 진동과 전체 획득 알림을 사용자가 구분할 수 있는지 반복 평가한다.
- 장시간 동작, 배터리 전원, 다섯 모터 최대 출력에서의 전원 안정성을 측정한다.

# QA: 마이크 전원 복구와 BLE 연결 알림

- 작성일: 2026-11-02 · 작성자: DH
- 작업 브랜치: `DH-1279/2026-11-02`
- 배포: 원격 최신 `0274b27`을 받은 뒤 QA 수정사항을 같은 개인 브랜치에 반영한다. main 및 김가네 브랜치 병합은 하지 않는다.
- 마이크: 사용자 확인 **GM20U**.

## 1. 요구사항

1. 준비음의 길이는 250ms로 유지하고 파형 진폭만 12,000에서 6,000으로 낮춘다.
2. 실제 BLE 미연결 중에는 준비음을 내지 않고 연결 상태 때문에 소리가 반복되지 않게 한다.
3. BLE 연결 완료 시 장갑이 한 번 짧게 진동한다.
4. 시연할 때만 마이크 전원을 켜도 사용할 수 있도록 입력을 자동 복구한다.

## 2. 마이크에서 확인한 코드 문제

기존 통합 실행기는 `sounddevice` 장치 인덱스 1을 고정 사용했다. 입력 스트림의 종료 콜백은 음성 서비스 전체의 `_stop`을 설정했다. 이후 마이크가 다시 나타나도 입력을 다시 여는 경로가 없었다. USB 재인식으로 숫자 인덱스가 달라지는 상황도 처리하지 않았다.

이는 코드에서 확인한 복구 취약점이다. GM20U 스위치가 USB 장치를 제거하는지, 음소거만 하는지, 실제 사용자 환경에서 어떤 오류가 발생했는지는 아직 실측하지 않았다.

## 3. 마이크 입력 변경

- `alsa_input.py`에 별도 입력 작업을 추가했다.
- 통합 실행기에서 `arecord -D plughw:CARD=GM20U,DEV=0`으로 캡처한다.
- 카드 번호가 아니라 카드 ID를 사용하므로 동일 장치의 숫자 번호 변경에 의존하지 않는다.
- 입력은 기존과 같은 16kHz·모노·PCM16이며 20ms 블록으로 전달한다.
- 마이크가 없어도 프로그램 초기화를 계속한다.
- 녹음 프로세스 종료·입력 종료·2초간 PCM 중단 시 정리한 뒤 2초 간격으로 재시도한다. 장애 감지·프로세스 정리·장치 재인식 시간은 별도로 필요하다.
- 실제 PCM이 들어오면 연결 복구로 처리한다. 무음 PCM도 정상 입력이므로 기계식 음소거를 USB 분리로 오판하지 않는다.
- 분리·재연결 때 이전 PCM과 VAD를 비우고 세대 번호를 변경해 이전 인식 결과를 수락하지 않는다.
- 마이크 상실 자체는 TTS·영상·BLE 작업 전체를 종료하지 않는다.
- 화면의 `Audio: WAITING_MIC`과 로그로 대기 상태를 확인한다. TTS 재생 중에는 SPEAKING이 먼저 표시될 수 있다.
- 종료 시 녹음 프로세스와 입력 작업도 정리한다.

이 복구는 `input_backend="alsa"` 설정에 적용한다. 기존 `sounddevice` 경로는 호환성을 위해 유지한다. 녹음은 메모리로 전달하며 이번 기능이 음성을 영구 저장하지는 않는다. TTS 재생 장치 `output_device`는 변경하지 않았다.

장치 지정과 PCM 옵션은 [Debian arecord 문서](https://manpages.debian.org/trixie/alsa-utils/arecord.1.en.html)를 기준으로 했다.

## 4. 준비음과 BLE 상태

- 준비음은 **250ms, 진폭 6,000**이다. 체감 음량이 정확히 절반이라는 뜻은 아니며 실제 스피커에서 확인한다.
- 실제 BLE가 미연결·끊김·펌웨어 불일치 상태일 때 입력 준비음을 억제한다.
- BLE 상태 이벤트를 TTS 큐에 반복 추가하지 않고 화면·로그로 표시한다.
- 준비음 억제는 음성 명령 입력을 막지 않는다.
- 연결 이벤트만으로 준비음을 새로 예약하지 않는다.
- 연결 후 일반 음성 응답이 끝나면 준비음을 사용할 수 있다.
- `--no-ble`·`--dry-run`은 음성 자체의 시험을 위해 준비음을 사용할 수 있다.
- 시작 안내에서 준비음이 반드시 나온다고 전제하는 문장을 제거했다.

## 5. BLE 연결 확인 진동

초기 STOP·상태 읽기·capability 검사를 마친 실제 연결에서 전체 모터를 **duty 180, 200ms 한 번** 울린다. 획득 알림의 최대 출력 두 번과 구분한다.

기존 ESP의 mode 2 다중 FAR 패턴을 사용한다. ON 200ms·주기 1,200ms에 TTL 300ms를 적용해 STOP 응답이 늦어도 두 번째 진동이 시작되지 않게 한다. Pi는 짧은 대기 후 STOP을 보낸다. 명령 응답 시간 초과 등 실제 통신 실패 시에는 기존 정리·자동 재연결 경로를 따른다.

연결 진동이 끝난 뒤에 안내를 활성화하고, 이전 좌표를 폐기한 후 새 프레임으로 안내한다. 정상 연결 세션마다 한 번이며 검색 재시도마다 진동하는 방식은 아니다. `--dry-run`과 ESP DRY_RUN에서는 실제 연결 진동을 내지 않는다.

기존 `caps=07` 수신기를 사용하므로 **ESP 펌웨어 재업로드는 필요 없다.** 독립 검사 `python -m ble_sender.check_link`는 여전히 STOP과 상태 읽기만 수행하며 연결 확인 진동을 보내지 않는다.

## 6. 검증과 실기기 시험

로컬 관련 테스트 100개 통과. 실제 펌웨어 패턴 엔진에서도 연결 진동이 200ms 뒤 OFF되고 STOP 없이도 반복되지 않는지 검사했다. USB 입력은 모의 프로세스·PCM으로 검사했으며 실제 GM20U 시험 완료를 의미하지 않는다.

- [ ] 마이크 OFF 상태에서 앱을 실행해 화면이 뜨고 WAITING_MIC으로 기다리는지
- [ ] 마이크 ON 후 입력이 복구되어 시동어가 인식되는지
- [ ] 마이크 OFF/ON을 여러 번 반복해 앱 재시작 없이 복구되는지
- [ ] USB를 실제로 분리·재연결해 카드 번호가 바뀌어도 복구되는지
- [ ] 기계식 음소거만 하는 경우 무음 때문에 재연결을 반복하지 않는지
- [ ] BLE 미연결 중 상태 알림·준비음이 반복되지 않는지
- [ ] 장갑 연결 후 200ms 한 번, 획득 후 350ms 두 번이 구분되는지
- [ ] 끊김·재연결 후에도 연결 확인 진동이 한 번만 발생하는지
- [ ] 연결 확인 중 종료·통신 실패 시 모터가 정지하는지

Pi에서 `arecord -l`의 카드 ID가 GM20U인지 확인한다. 다른 녹음 앱이 점유하면 자동 재시도하므로 시험용 녹음 명령을 detector와 동시에 실행하지 않는다. 실제 복구 시간과 체감 음량은 위 시험에서 확인한다.

원격 `0274b27`의 10클래스 라벨 변경과 휴대폰 탐지 제외 코드를 보존했다. 음성 물체 목록에는 여전히 이전 11종이 있어 새 모델의 mouse·Sunglasses 등을 음성으로 선택하려면 별도 정합 수정이 필요하다. 이번 QA에서는 해당 목록을 변경하지 않는다.

# Raspberry Pi → ESP32-C3 BLE LED 시험

모터가 도착하기 전에 Raspberry Pi에서 입력한 명령으로 ESP32-C3 SuperMini의 내장 LED를 제어한다. 카메라와 영상 처리는 아직 실행하지 않는다.

- 작업일: 2026-09-17 (한국 시간)
- 결과: **BLE 연결, 반복 명령 송수신, 실제 LED ON/OFF, 종료 후 재연결 성공**
- 근거: 사용자가 제공한 Arduino 업로드 로그와 Pi 실행 로그, 실제 LED 동작 및 재연결에 대한 사용자 확인
- Pi 프로젝트 기본 위치: `~/Desktop/kimGA_raspi`
- 작업 브랜치: `DH-1279/2026-09-17`

## 오늘 진행한 작업

1. Raspberry Pi SD 카드 준비 후 기본 설정과 Tailscale 설정을 완료했다고 사용자가 확인했다. Tailscale은 Pi 원격 접속용이고, ESP32와의 시험 통신은 BLE로 진행했다.
2. 장갑에 작은 제어 명령을 전달하는 첫 통신 방식으로 BLE를 선택했다. 영상 처리는 Pi에서 맡고 ESP32에는 제어 명령만 보내는 방향이다.
3. ESP32 수신 스케치와 Pi 송신 프로그램을 작성하고, Pi에서는 Git으로 코드를 받아 Python 가상환경에서 실행했다.
4. Arduino IDE의 NimBLE 라이브러리 누락을 해결하고 ESP32에 펌웨어를 업로드했다.
5. Pi의 `on/off/status` 명령으로 통신과 상태 응답을 확인했다. 사용자는 실제 내장 LED의 점등·소등도 확인했다.
6. Ctrl+C 종료 과정의 OFF 응답을 확인했고, 사용자는 프로그램 재실행 후 재연결도 성공했다고 확인했다.

## BLE를 먼저 선택하는 이유

| 항목 | BLE | Wi-Fi |
| --- | --- | --- |
| 이번에 보낼 데이터 | LED ON/OFF, 이후 손가락별 진동 명령 같은 작은 데이터에 적합 | 작은 명령 전송도 가능 |
| 연결 구성 | Pi와 장갑 직접 연결, 공유기 불필요 | 공유기 또는 AP와 IP 설정 필요 |
| 향후 방향 | 배터리 장갑의 첫 후보 | 웹 화면, 많은 로그·데이터 전송이 필요할 때 검토 |

우선 BLE로 연결·재연결·응답을 확인한다. 실제 소비전력과 지연은 연결 설정과 동작 방식에 따라 달라지므로 측정 후 판단한다. 카메라 영상은 Raspberry Pi에서 처리하고, ESP32에는 제어 명령만 보낸다. Pi를 Wi-Fi로 원격 접속해도 장갑과의 연결은 BLE로 사용할 수 있다.

## 1. ESP32 준비

1. Arduino IDE의 라이브러리 관리자에서 `NimBLE-Arduino`를 검색하고 작성자 `h2zero`, 버전 `2.5.1`을 설치한다. Espressif 보드 패키지와 별도 라이브러리다.
2. 위 `ble_led_control.ino`를 연다.
3. 보드 `ESP32C3 Dev Module`, `USB CDC On Boot → Enabled`, 현재 ESP32 포트를 선택한다. 이전 포트는 COM11이었지만 재연결 후 달라질 수 있다.
4. 업로드하고 시리얼 모니터를 **115200 baud**로 연다.
5. 시작 메시지를 놓쳤다면 RESET을 한 번 누른다.

```text
BLE ready | name=KIMGANE-LED | LED=OFF
MEM | free_heap=... | min_free_heap=... | uptime_ms=...
```

이번 스케치는 자동으로 깜빡이지 않는다. Pi에서 `on`을 보내기 전에는 LED가 꺼져 있는 것이 정상이다. 일반적인 C3 SuperMini의 GPIO8, LOW일 때 켜지는 LED를 기준으로 한다. 전원 표시 LED는 제어 대상이 아니다.

## 3. 명령 보내기

프로그램은 8초 동안 검색한 뒤 연결한다. `KIMGANE-LED`라는 이름을 표시하며, 실제 대상 식별은 전용 서비스 UUID로 한다.

```text
명령 [on/off/status/quit]> on
LED ON 확인 | 쓰기+읽기 ... ms
명령 [on/off/status/quit]> off
LED OFF 확인 | 쓰기+읽기 ... ms
명령 [on/off/status/quit]> status
LED OFF
명령 [on/off/status/quit]> quit
```

- `on` 또는 `1`: LED 켜기
- `off` 또는 `0`: LED 끄기
- `status`: ESP32가 보고하는 LED 상태 읽기
- `quit` 또는 `q`: LED를 끄고 연결 종료
- Ctrl+C도 종료 가능

`on` 상태는 다음 명령 또는 연결 해제까지 유지한다. 연결 손실을 ESP32가 감지하면 LED를 끄고 다시 검색 가능한 상태로 돌아간다. 갑자기 멀어지거나 Pi 전원이 꺼지면 연결 손실 감지까지 시간이 걸릴 수 있다. 끊겼다면 프로그램을 다시 실행한다.

같은 펌웨어의 장치가 여러 개 검색되면 프로그램이 주소를 출력하고 중단한다. 대상 주소를 지정한다.

```bash
python led_control.py --address AA:BB:CC:DD:EE:FF
```

주소는 실제 검색 결과로 바꾼다. 업로드 로그의 MAC 주소가 BLE 주소와 같다고 가정하지 않는다.

## 확인할 결과

1. `on/off`에 맞춰 ESP32의 제어 가능한 내장 LED가 실제로 켜지고 꺼지는지 확인한다.
2. ESP32 시리얼의 `RX | LED=ON/OFF`와 Pi의 상태 읽기 결과가 일치하는지 확인한다.
3. `quit` 후 LED가 꺼지고, 프로그램 재실행으로 다시 연결되는지 확인한다.
4. 반복 조작하며 ESP32가 재부팅되지 않는지, `free_heap`이 지속적으로 감소하는지 관찰한다. `min_free_heap`은 부팅 이후 최저치여서 다시 올라가지 않는 것이 정상이다.

Pi에 표시되는 시간은 **쓰기 응답과 상태 읽기까지 포함한 왕복 작업 시간**이다. 무선 편도 지연이나 물리적인 LED 점등 시간을 직접 측정한 값은 아니다. 상태 읽기 또한 GPIO에 적용한 논리 상태를 보고하므로 실제 빛은 눈으로 확인해야 한다.

앞선 기본 스케치의 프로그램 22%는 프로그램 저장 공간 사용량이었다. 전역 변수 4%도 실행 중 BLE가 동적으로 사용하는 메모리를 모두 포함하지 않는다. 이번에는 연결 전·후의 `free_heap`을 함께 본다.

## 구현 범위와 다음 단계

현재 프로토콜은 ASCII `0`/`1` 한 바이트를 쓰고 동일 특성에서 상태를 읽는다. 테스트용 연결이며 인증/암호화를 요구하지 않는다. 현재 코드를 모터에 바로 연결하지 않는다. 모터 단계에서는 5채널 세기 명령, 명령 유효시간, 통신 중단 시 정지, 적절한 전원과 드라이버를 추가한다.

실제 Pi ↔ ESP32 연결, 내장 LED ON/OFF 및 종료 후 재연결까지 확인했다. 다음 단계 후보는 손가락별 진동 세기 5개를 전송하고, 모터 대신 ESP32 시리얼 출력으로 수신값을 검증하는 것이다. 아직 5채널 명령 구현이나 모터 구동 시험은 진행하지 않았다.

| Ctrl+C 종료 | 종료 처리에서 OFF 명령과 상태 응답 확인 |
| 종료 후 재실행·재연결 | 사용자 확인 완료 |

수동 ON/OFF 8회의 쓰기+읽기 시간은 **157.1~205.2ms**였다. 연결 직후 초기 OFF는 539.7ms, 종료 시 OFF는 151.3ms로 별도 기록한다. 이 값은 Python·운영체제·BLE 쓰기 응답·상태 읽기를 포함하며, LED 점등까지의 편도 지연이나 향후 모터 구동 지연을 뜻하지 않는다. 이번 소규모 수동 시험만으로 장시간 안정성이나 실시간 성능을 보장하지 않는다.

### 발생한 문제와 해결

| 문제 | 확인 및 처리 |
| --- | --- |
| `NimBLEDevice.h: No such file or directory` | 사전 검증은 임시 라이브러리를 사용했지만 Arduino IDE의 사용자 라이브러리에는 설치되지 않은 상태였다. IDE가 사용하는 `Documents/Arduino/libraries`에 NimBLE-Arduino 2.5.1 설치 후 헤더 존재 확인. 이후 사용자 컴파일·업로드 성공 |
| 긴 컴파일 대기와 `User abort` | 해당 문구만으로 중단 원인을 확정할 수 없었다. 이후 화면에서 컴파일 단계임을 확인하고 상세 로그 활성화를 안내했다. 최종 로그에서 컴파일, COM11 연결, 기록 및 해시 검증 성공 확인 |
| 업로드 설정 확인 | 보드, COM11, USB CDC, 4MB 플래시 설정을 확인했고, 921600 baud에서 최종 업로드 성공 |
| Pi 코드 배포 방식 | 사용자의 요청대로 Git clone/pull로 통일하고 실제 경로 `~/Desktop/kimGA_raspi/microprocessor-capstone-design` 반영 |

아직 확인하지 않은 항목은 전원 차단·거리 이탈 시 동작, 장시간 연결 안정성, 실행 중 힙 사용량, 소비전력 및 실제 모터 5개 구동이다. 이번에 확인한 재연결은 정상 종료 후 프로그램을 다시 실행한 경우다.

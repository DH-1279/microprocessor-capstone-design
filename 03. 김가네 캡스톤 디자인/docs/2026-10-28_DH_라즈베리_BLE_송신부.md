# 라즈베리 BLE 송신부 및 detector 자동 연결

작성일: 2026-10-28 / 작성: DH

작업 브랜치: `DH-1279/2026-10-28`

통합 대상 브랜치: `KimGA_raspi/2026-10-27`

기준: 김가네 `cac9959`의 최신 영상·음성 흐름과 [ESP32 BLE v2 수신 규격](2026-10-27_DH_ESP32_BLE_송수신규격.md).

## 1. 현재 통합 상태

**`KHS_KMJ_vision/detector.py`를 실행하면 BLE 작업도 자동으로 시작한다.** 별도 송신 터미널을 열거나 `python -m ble_sender`를 함께 실행할 필요가 없다.

```text
detector.py 실행
 → 내부 BLE 작업 시작 → ESP32 검색·연결 → 초기 STOP·상태 확인
 → 카메라·음성 초기화 → 시동어 대기
 → 물체 선택·락온 → 유효한 손/목표 좌표를 BLE 작업으로 전달
 → 2안/3안 명령 갱신 → ESP32가 선택 모터의 PWM 패턴 생성
```

시작할 때 연결 실패 시에는 BLE 없는 실행으로 조용히 넘어가지 않고 오류로 종료한다. 한번 연결된 뒤 안내 중 통신 오류가 생기면 진동 연결을 해제하고 영상·음성은 유지한다. ESP 없이 처음부터 영상·음성만 확인하려면 명시적으로 `--no-ble`을 쓴다. 시동어·목표 선택 전에는 연결되어 있어도 진동 안내를 시작하지 않는다.

해수의 현재 흐름을 유지했다.

- 시동어 뒤 물건 선택 안내와 현재 목록을 한 번 재생한다. “리스트” 요청도 처리한다.
- 탐색 중 취소하면 시동어 대기로 돌아간다. 물건 이름만 말해서는 안내가 재시작되지 않는다.
- 도달 판정 후에는 시동어 대기로 돌아가며, 다른 물건을 찾으려면 캡스톤을 말하도록 안내한다.
- 손 미인식 음성은 기존 5초 간격을 유지한다.
- 미리보기는 전체화면으로 표시하며 시작 시 볼륨 100% 설정을 시도한다. 각 믹서 명령에는 2초 제한이 있다.

목록의 3초 자동 반복이나 프로그램 설명 확장은 이번 통합에서 추가하지 않았다.

```bash

cd "03. 김가네 캡스톤 디자인/Raspi5_vision"
source .venv/bin/activate

```

로컬에 브랜치가 없으면 `git switch`가 같은 이름의 원격 브랜치를 따라 생성한다. 기존 가상환경이 다른 위치에 있으면 그 `.venv/bin/activate`의 절대 경로를 사용하고, 실행 폴더는 위 `Raspi5_vision`으로 맞춘다. 카메라·Hailo·MediaPipe·음성의 기존 모델 및 의존성은 그대로 필요하다.

## 3. 실행은 detector 하나

```bash
python -u KHS_KMJ_vision/detector.py --mode 2
```

기본 모드는 2이므로 `--mode 2`를 생략해도 된다. ESP에는 `esp32_device/ble_final/firmware/ble_final_receiver`가 올라가 있어야 한다. BLE 이름 `KIMGANE-HAPTIC-V2`와 서비스 UUID로 자동 검색한다. 장치가 여러 개면 다음처럼 주소를 지정한다.

```bash
python -u KHS_KMJ_vision/detector.py --address XX:XX:XX:XX:XX:XX --mode 3
```

PuTTY에서 실행하면서 라즈베리에 연결한 HDMI 모니터로 미리보기를 볼 때는 기존처럼 다음 환경을 먼저 지정한다.

```bash
export DISPLAY=:0
export XDG_RUNTIME_DIR="/run/user/$(id -u)"
python -u KHS_KMJ_vision/detector.py
```

ESP가 `DRY_RUN=true`면 연결·논리 상태만 확인되고 실제 모터는 켜지지 않는다. 실제 모터 시험은 점검된 PCB에서 `DRY_RUN=false`로 업로드한다. **Pi의 `--dry-run`은 BLE 연결 자체를 생략하는 옵션**으로 ESP 펌웨어 설정과 다르다.

```bash
# ESP 없이 카메라·음성과 송신 매핑을 검사
python -u KHS_KMJ_vision/detector.py --dry-run
# 송신 작업 없이 기존 영상·음성만 실행
python -u KHS_KMJ_vision/detector.py --no-ble
```

## 4. 같은 터미널에서 모드 전환

ESP 시리얼 모니터가 아닌 **detector를 실행한 라즈베리 터미널**에 입력하고 Enter를 누른다.

| 명령 | 동작 |
|---|---|
| `mode 2` | 고정 손가락의 진동 간격 안내 |
| `mode 3` | 방향별 손가락 + 근접 두 번 진동 |
| `status` | 송신부 상태와 ESP 상태 패킷 조회 |
| `stop` | 즉시 정지, 새 영상이 와도 정지 유지 |
| `resume` | 터미널 정지 해제, 이후 새 프레임부터 안내 |
| `reconnect` | 통신 중단 상태에서 ESP 재연결. 이후 `resume`이 별도로 필요 |
| `quit` | BLE 정지 후 detector도 종료 |

미리보기 창의 `q` 또는 Ctrl+C도 전체 종료 경로에서 BLE를 닫는다. 음성 “취소”는 시동어 대기 복귀이며, 터미널 `stop`은 모터 안내의 수동 잠금이다. 잠금 중에는 음성으로 다시 목표를 골라도 `resume` 전까지 진동하지 않는다.

서로 다른 모드로 바꾸면 먼저 STOP을 전송하고 이전 좌표를 폐기한다. 이후 새로 촬영한 프레임으로 안내를 재개한다. 같은 모드를 다시 입력하면 패턴을 재시작하지 않는다.

## 5. 좌표와 동작 기준

BLE 코드는 `Raspi5_vision/ble_sender/`에 유지한다. detector는 같은 프로세스의 별도 작업 스레드에서 BLE 이벤트 루프를 실행한다. 영상 루프는 `VisionPublisher`로 Pi 내부 `127.0.0.1:8766`에 현재 관측을 전달한다. 카메라·Hailo·마이크를 중복해서 열지 않는다. 독립 송신 프로그램과 detector를 동시에 실행하면 같은 포트가 충돌하므로 둘 중 하나만 실행한다.

관측에는 새 프레임 번호, 원본 촬영 시각, 실제 화면 크기, 정규화된 손 21점과 목표 박스를 넣는다. 목표를 새로 락온할 때마다 다른 ID를 발급한다. 같은 이름의 물체라도 새 락온이면 이전 패턴·좌표를 이어받지 않는다.

손은 `hand="Any"`로 추적하여 장갑의 Left/Right 오분류를 허용한다. 물리적 착용 손 설정 `worn_hand="Left"`는 손바닥·손등 해석용이며 Right 라벨의 손을 거르는 설정이 아니다.

추적기에 `last_observed_landmarks`를 추가했다. 이번 프레임의 유효한 단일 손에만 값이 있고, 안정화 때문에 이전 손 위치를 유지한 프레임·여러 손·낮은 점수·잘못된 좌표에는 없다. detector의 BLE와 도달 판정은 이 관측을 사용한다. 화면 표시를 위한 기존 raw 값과 안정화 기능은 유지한다.

### 2안: 고정 검지 + 간격

검지 끝에서 목표 박스까지 영상상 최단 거리를 손바닥 폭으로 나눈다. 기본 채널은 IN이며 `--rate-channel TH` 등으로 바꿀 수 있다. 손을 뒤집어도 고정 채널을 유지한다.

| 구간 | ON | OFF |
|---|---:|---:|
| far | 200ms | 1000ms |
| middle | 200ms | 500ms |
| near | 200ms | 200ms |

### 3안: 손 기준 방향 + 근접

손 관절 축에 대해 목표 방향을 계산한다. 화면 회전과 가로세로 비율을 보정하며 MediaPipe의 Left/Right 라벨로 채널을 고르지 않는다.

| 방향 | 모터 |
|---|---|
| 엄지 쪽 | TH |
| 소지 쪽 | PI |
| 손끝 쪽 | IN |
| 손목 쪽 | RI |
| 영상상 근접 | MI, 120ms ON → 120ms OFF → 120ms ON 후 OFF |

근접은 손바닥 중심에서 목표 박스까지의 거리를 손바닥 폭으로 나눈 값이다. 기본 경계는 near=0.35, middle=1.5, 여유 0.10이며 방향은 3개 연속 새 프레임으로 확인한다. `--near`, `--middle`, `--stable-frames`로 조정한다. 손을 옆으로 세워 관절 축이 모호하면 정지한다.

현재 도달 판정은 기존의 **중지 밑 관절과 목표 중심 50px 이내, 5개 연속 프레임**을 유지하되, 새 유효 손·새 목표 관측이 있을 때만 누적한다. 도달 시 STOP이 근접 패턴보다 우선하므로 진행 중인 두 번 진동이 중간에 끝날 수 있다. 영상상 거리는 cm·깊이·접촉·실제 집기 완료를 증명하지 않는다.

## 6. 정지·지연·오류

- 안내 중 최대 10Hz로 새 sequence를 보내고 ESP TTL은 500ms다. 중간의 활성 채널 변경은 최신 것만 보내며 STOP은 우선 처리한다. 정지 상태에서는 같은 STOP을 반복하지 않는다. 실제 PWM 200Hz와 ON/OFF 패턴은 ESP가 생성한다.
- 현재 쓰기 응답(ACK) 대기는 최대 1초다. 이 시간은 ESP의 TTL을 연장하지 않는다. 응답을 기다린 뒤에는 현재 프레임을 다시 확인하므로 그동안 만료된 관측을 갱신 명령으로 재사용하지 않는다.
- 기본 프레임 최대 나이는 350ms다. 촬영 시각을 추론 종료/수신 시각으로 바꾸지 않는다. 영상 작업이 막혀도 BLE 작업이 독립적으로 오래된 관측을 만료한다.
- 손/목표 상실, 음성 취소, 도달, 실행 종료는 STOP이다. 이전 `locked_target_box`를 새 관측으로 재전송하지 않는다.
- 안내 중 연결/쓰기 응답 오류가 생기면 진동 연결을 해제하고 영상·음성은 계속한다. 중단 사실을 음성으로 알리고, `reconnect` 후 `resume`을 입력해야 새 프레임으로 안내를 재개한다. 자동 재접속·재개는 하지 않는다. 송신 작업이 완전히 멈추면 ESP TTL 만료가 마지막 방어다.
- `--max-age`를 늘리면 느린 추론을 수용하지만 오래된 위치로 안내하는 시간도 늘어난다. 실제 처리 지연을 확인한 뒤 조정한다.
- `--duties 180 180 180 180 180`은 TH/IN/MI/RI/PI 보정값이다. 각각 1..255, 한 번에 선택한 모터 하나에만 사용한다. 기본 180은 사용자 평가 전 시험값이다.
- ESP 상태의 ON/duty는 논리 출력이며 실제 전류·진동 측정값이 아니다.

## 7. 실물 시험 순서

1. ESP BLE v2 수신기를 켜고 detector만 실행해 연결 메시지를 확인한다.
2. 시동어 대기와 물건 선택 단계에서는 진동하지 않는지 확인한다.
3. “캡스톤” → 물건 이름으로 락온한 뒤 손을 보여 안내를 확인한다.
4. `mode 2`, `mode 3`을 바꾸고 손바닥/손등·방향·거리 구간을 비교한다.
5. 손을 가리거나 목표를 화면에서 빼서 정지를 확인한다.
6. 음성 “취소”, 터미널 `stop`/`resume`, 도달, `quit`를 각각 확인한다.

BLE·모터만 분리해서 검사하려면 detector를 종료한 뒤 `python -m ble_sender --mode 3 --allow-test`를 실행하고 `test middle th 2`, `test near mi 1`을 사용할 수 있다. 시험 명령은 최대 2초다.

## 8. 검증과 한계

PC 검사 40개가 통과했다. 실제 detector 루프에 카메라·음성·추론만 모의로 공급해 락온/취소/재선택/도달/손·목표 상실/오래된 프레임/예외 정지를 확인했다. 내부 BLE 작업과 실제 로컬 UDP를 연결한 검사, 초기화 실패와 연결 대기 중 종료 검사도 포함한다. 최신 취소의 시동어 재요청과 전체화면·볼륨 설정도 회귀 검사에 포함했다.

기존 ESP C++ 패턴 엔진과의 24개 유효 조합 × 80시점(1,920시점) 대조도 유지한다. 테스트는 아래 명령으로 실행한다.

```bash
python -m unittest discover -s ble_sender/tests -v
# C++ 컴파일러가 있으면 ESP 패턴 엔진 대조까지 포함:
c++ -std=c++17 -Wall -Wextra -Werror -shared -fPIC \
  ble_sender/tests/firmware_bridge.cpp -o /tmp/kimgane-ble-v2.so
HAPTIC_V2_LIB=/tmp/kimgane-ble-v2.so \
  python -m unittest discover -s ble_sender/tests -v
```

라즈베리 Bluetooth 어댑터·실제 ESP 무선 연결·장갑 모터 체감은 이 PC 검사에 포함하지 않았다. 실제 기기에서는 위 7절 순서로 확인해야 한다.

## 9. 실기 연결 시간 초과 점검

10월 28일 실기에서 BLE 광고 이름·서비스 UUID는 검색됐지만 `connect()`의 기존 15초 제한에 걸렸다. ESP가 `flags=11`이었다가 `10`으로 돌아온 것도 확인했다. 이는 DRY_RUN 상태에서 연결됐다가 해제된 상태 변화이며, 그 변화만으로 재부팅을 뜻하지 않는다.

이후 연결·GATT 서비스 확인의 기본 제한을 30초로 설정하고, 송신부 전체 초기화 대기를 검색 시간+연결 시간+12초로 맞췄다. 기본값에서는 52초다. 단계별 진행 로그를 표시하고, 빈 `TimeoutError`도 예외 종류를 표시한다. 검색·연결 제한은 `--scan-timeout`, `--connect-timeout`으로 지정한다.

시간 제한 조정은 실제 무선 연결 성공을 입증하지 않는다. ESP의 연결 이벤트가 먼저 나타나더라도 Pi의 연결/GATT 확인이 끝나기 전에 시간이 초과될 수 있다. 다음처럼 detector 없이 BLE만 먼저 검사하면 영상·음성과 분리해 확인할 수 있다 (`Raspi5_vision`에서 실행).

```bash
BLEAK_LOGGING=1 python -u -m ble_sender \
  --address 9C:CC:01:82:75:8A --connect-timeout 30 --no-console
```

정상이면 검색 → 연결·서비스 확인 완료 → 초기 STOP/상태 확인 → BLE 연결 메시지가 나온다. Ctrl+C로 종료한 뒤 detector를 실행한다. BLE 시험과 detector를 동시에 켜지 않는다.

계속 실패하면 마지막 단계 로그와 ESP의 flags 변화, 아래 장치 정보·BlueZ 로그를 함께 확인한다. USB 전원 재인가 후 한 프로그램으로만 연결을 시험한다. Wi-Fi를 통해 원격 접속 중이라면 Wi-Fi를 끄는 방식의 진단은 진행하지 않는다.

```bash
bluetoothctl info 9C:CC:01:82:75:8A
journalctl -u bluetooth --since "3 minutes ago" --no-pager
```

연결/상태 읽기 시간 초과의 단계 구분, 초기화 시간 예산, 정리 중 오류가 원래 오류를 가리지 않는지를 추가 검사해 총 45개가 통과했다. ESP 펌웨어와 모터 패턴은 변경하지 않았다.

참고: [Bleak 연결 API](https://bleak.readthedocs.io/en/stable/api/client.html), [Bleak Linux 백엔드](https://bleak.readthedocs.io/en/develop/_modules/bleak/backends/bluezdbus/client.html), [공식 문제 해결 문서](https://bleak.readthedocs.io/en/stable/troubleshooting.html).

## 10. 연결 후 초기 STOP 시간 초과 점검

다음 실기 로그에서는 연결·GATT 서비스 확인이 완료됐고, 첫 STOP 쓰기에서 기존 0.3초 제한에 걸렸다. 이 응답 지연의 원인은 아직 확정하지 않았다.

초기 STOP과 초기 상태 읽기는 각각 최대 5초로 분리했다. 첫 STOP은 출력을 켜지 않으므로 초기 ATT 응답에 여유를 주되, 실제 안내 중 쓰기는 0.3초를 유지한다. ESP TTL 500ms와 영상 신선도 기준도 그대로다. 초기화 실패 뒤에는 막힌 ATT 요청에 STOP을 다시 쓰지 않고 연결을 해제한다. 전체 초기화 예산은 검색+연결+17초로 조정해 기본 57초다.

새 점검 명령은 `Raspi5_vision`에서 실행한다. 이미 `KHS_KMJ_vision` 폴더라면 먼저 `cd ..` 한다.

```bash
python -u -m ble_sender.check_link --address 9C:CC:01:82:75:8A
```

이 명령은 STOP과 상태 읽기만 사용한다. 카메라·Hailo·음성은 열지 않는다. 정상이라면 상태 읽기 3회의 시간·flags·duty를 표시한 뒤 연결을 종료한다. 이후 detector를 실행해 비교한다.

0.3초보다 느린 첫 STOP의 수락, 안내 중 0.3초 제한 유지, 실패한 초기 쓰기 중복 방지, 단독 점검 명령의 STOP 전용 동작까지 총 49개 검사가 통과했다. 실제 Pi–ESP 통신의 재시험은 별도로 필요하며 ESP 펌웨어는 변경하지 않았다.

## 11. 안내 중 TimeoutError로 detector가 종료되던 문제

실물 모터 구동 중 손을 돌릴 때 쓰기 응답이 0.3초 제한을 넘었고, BLE 작업의 예외가 detector 전체 종료로 이어졌다. 손 방향 변화가 응답 지연의 직접 원인인지는 아직 확인하지 않았다.

안내 중 통신 시간 초과·연결 상실에서는 진동 연결만 해제하고 영상·음성을 유지한다. 출력은 연결 해제 및 기존 ESP TTL로 정지하며, 진동 안내 중단을 음성으로 알린다. 통신이 멈춘 ATT 요청에 정지 쓰기를 재시도하지 않는다.

복구는 같은 터미널에서 다음 순서로 진행한다.

```text
reconnect
# 재연결 완료 메시지 확인 후:
resume
```

재연결만으로 모터를 켜지 않는다. `resume` 이후 새로 촬영한 유효 관측으로 재개한다. 통신 중단 상태에서도 `mode 2`, `mode 3`, `status`, `stop`, `quit`를 사용할 수 있다. 재연결 전에는 `resume`과 독립 진동 시험을 거절한다.

채널·구간이 바뀌어도 활성 명령은 최대 10Hz로 합치고, 정지는 우선 처리한다. 대기 중에는 불필요한 STOP 갱신을 하지 않는다. 응답 제한 0.3초, 프레임 나이 제한 350ms, TTL 500ms는 늘리지 않았다. 오류 로그에는 마지막 sequence·mode·zone·channel·duty를 포함해 실제 지연 위치를 확인할 수 있게 했다.

기본 모드 2는 IN 한 채널이다. 손을 돌리거나 다른 손가락이 물체에 가까워져도 채널이 바뀌지 않는다. 정상 출력의 예는 `mode=2 ch=1`, `duty=0,180,0,0,0`이다. 이때 실제 엄지까지 울리면 손가락에 붙인 모터의 위치와 채널 배선이 일치하는지 확인해야 한다. 아직 실제 배선 상태나 재부팅 유무는 확인하지 않았다.

재시험에서 오류 직전·직후 ESP의 `V2 | ...` 몇 줄을 남긴다. `ESP-ROM` 또는 `BLE V2 | READY | MOTORS`가 다시 나타나면 ESP 재부팅 가능성도 따로 점검한다. 구동 전원·순간 전류 문제와 무선/OS 지연을 이번 로그만으로 구분하지 않는다.

모의 통신 장애 후 detector 유지와 중단 음성, 명시적 재연결·재개, 채널 변경 합치기와 정지 우선 처리, 대기 중 반복 쓰기 제거까지 총 55개 검사 및 정적 검사가 통과했다. 실제 기기에서 동일 증상이 재현되는지 확인은 남아 있다.

## 12. 수신 성공과 늦은 응답을 분리

후속 실기에서 ESP의 마지막 수신 번호가 `seq=168`이고, Pi의 실패한 쓰기도 `seq=168`이며 응답 대기 0.301초였다는 로그를 확보했다. 명령은 ESP에 수락됐지만 같은 쓰기의 응답 완료가 기존 0.3초 안에 돌아오지 않은 경우다. 이를 전달 실패로 간주해 연결을 해제하던 기준을 수정했다.

안내 중 GATT 쓰기 응답 대기는 최대 1초로 조정했다. 응답이 0.3초보다 늦어도 1초 안에 완료되면 연결을 유지하며, 지연 로그는 최대 5초에 한 번 표시한다. 1초를 넘는 응답 실패에서는 앞 절처럼 진동 연결을 해제하고 영상·음성을 유지한다.

ESP TTL 500ms와 프레임 나이 제한 350ms는 변경하지 않았다. ACK 대기 동안 갱신이 멈추면 ESP 출력은 TTL로 만료될 수 있다. 응답 후에는 최신 관측을 다시 평가하며, 그 사이 만료된 관측을 새 명령처럼 보내지 않는다. TTL은 ESP의 수신 시각부터 계산되므로 무선 전달 지연까지 포함한 절대 촬영 나이를 보장하는 기능은 아니다.

0.35초 응답이 연결을 끊지 않는 회귀 검사, 늦은 응답 뒤 오래된 관측을 재전송하지 않는 검사, 호스트가 ACK를 기다리는 동안 실제 ESP C++ 엔진의 TTL이 만료되어 출력이 0이 되는 검사를 추가했다. 총 58개 검사 및 정적 검사가 통과했다.

사용자는 PCB도 손과 함께 회전한다고 확인했다. 응답이 늦어진 물리적 원인을 안테나·배선·전원·호스트 처리 중 하나로 확정한 것은 아니다. PCB를 고정하고 손만 돌리는 비교 시험과 실제 ACK 지연 로그를 남긴다. ESP 펌웨어를 다시 업로드할 필요는 없다.

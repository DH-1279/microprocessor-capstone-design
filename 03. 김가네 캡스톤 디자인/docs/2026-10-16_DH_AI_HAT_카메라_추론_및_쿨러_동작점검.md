## 2. 실행 중 발생한 오류와 수정

| 발생한 문제 | 확인 내용·원인 | 조치와 결과 |
|---|---|---|
| `FileNotFoundError: .../labels.txt` | 라벨을 기록하려는 `/tmp/kimgane-khs-check` 폴더가 없었음. 폴더가 없어진 이유는 확정하지 않음 | 폴더를 생성하고 HEF·라벨을 다시 준비 |
| `AttributeError: 'Device' object has no attribute 'identify'` | 코드가 설치된 HailoRT Python API와 다른 호출 경로를 사용 | `physical.control.identify()`로 수정. 이후 모델 로딩 성공 |
| `ValueError: Expected normalized, ordered NMS coordinates` | 기존 검사는 모든 NMS 좌표가 0~1 안에 있어야 한다고 가정. Hailo YOLOv8 디코더는 경계 밖 좌표를 출력할 수 있음을 공식 구현에서 확인 | Hailo NMS 경로에서 경계 밖 좌표를 허용하고 원본 영상 범위로 잘라내도록 수정. 이후 152프레임 실행에서 재발 없음 |
| 기본 10프레임으로 관찰 시간이 짧음 | 물체를 카메라에 보여주며 확인하기에는 실행 시간이 짧았음 | `--frames 300`으로 늘리고 외부 제한을 `timeout 180s`로 설정 |

좌표 오류 당시의 원시 NMS 행은 확보하지 못했으므로, 정확히 어떤 값이 예외를 일으켰는지는 확정하지 않았다. 수정은 공식 디코더의 경계 처리 방식과 코드의 과도한 범위 제한을 근거로 진행했다.

수정 후에도 NaN·무한대, 뒤집힌 좌표, 잘못된 클래스 수·출력 형식은 오류로 처리한다. 영상과 겹치지 않거나 면적이 없는 박스는 제외한다. 좌표 복원 함수의 다른 호출 경로에는 기존의 엄격한 범위 검사를 유지했다.

115개는 같은 물체를 여러 프레임에서 탐지한 항목을 포함한다. 서로 다른 실물 115개를 인식했다는 의미가 아니다. 또한 91/152는 정확도나 재현율이 아니다. 실제 화면의 정답과 비교하지 않았으므로 모델 성능 수치로 사용하지 않는다.

### 대표 출력

```text
모델 로딩 성공 | 입력 640×640 | 클래스 18개
프레임 11/300 | 추론 13.6ms | 탐지 2개
  watch | 신뢰도 0.67 | 좌표 (0.028, 0.054, 0.913, 0.208)
  cell phone | 신뢰도 0.56 | 좌표 (0.796, 0.129, 1.0, 0.857)
...
프레임 152/300 | 추론 13.5ms | 탐지 0개
^C
사용자 요청으로 점검을 중단했습니다.
```

출력 좌표는 원본 영상 기준의 정규화된 `(x1, y1, x2, y2)`다. 영상 가장자리를 넘어가는 박스는 0~1 범위로 잘리므로 `1.0` 같은 경계값이 나올 수 있다. 값이 출력된 사실만으로 실제 물체와 박스가 정확히 일치한다고 판단하지 않는다.

처리 시간은 `detector.detect(rgb)` 호출에 소요된 시간으로, 전처리·HAT 실행·결과 해석을 포함한다. 카메라 읽기, 터미널 출력, 프레임 사이 대기는 포함하지 않는다. 따라서 **약 13.6ms를 전체 시스템의 70FPS 이상 처리 성능이나 종단 간 응답 시간으로 해석하지 않는다.**

카메라 초기화 때 `Unsupported V4L2 pixel format Nc30`, `Nc12` 경고가 있었지만, 이어서 스트림 설정과 추론이 진행됐다. 이번 로그에서는 실행을 중단시킨 오류가 아니었다.

## 4. 액티브 쿨러 설치 및 시험

액티브 쿨러 설치 후 온도 설정과 회전 센서값을 확인했다.

```bash
grep -H . /sys/class/thermal/thermal_zone0/trip_point_*_temp
grep -H . /sys/class/hwmon/hwmon*/fan1_input 2>/dev/null
```

| 조회 항목 | 실제 출력 |
|---|---|
| `trip_point_0_temp` | 110000 |
| `trip_point_1_temp` | 50000 |
| `trip_point_2_temp` | 60000 |
| `trip_point_3_temp` | 67500 |
| `trip_point_4_temp` | 75000 |
| 팬 장치 이름 | `pwmfan` |
| 최초 회전수 출력 | 2623 RPM |
| 이후 모니터 화면 | CPU 49.6°C, 팬 2726 RPM |

`trip_point_0`의 110°C는 팬 시작 온도로 해석하지 않는다. 또한 센서값만으로 사용자가 보고한 “팬이 안 도는 것 같다”는 관찰을 해소했다고 판단하지 않고, 최대 출력 시험을 추가했다.

### 10초 최대 출력 시험

시험 스크립트는 PWM을 최대값으로 유지하며 매초 회전수를 출력하고, 종료 시 이전 PWM 값으로 복원하도록 실행했다. 실제 출력은 다음과 같다.

```text
1초  7867 RPM
2초  8736 RPM
3초  8849 RPM
4초  8865 RPM
5초  8891 RPM
6초  8925 RPM
7초  8965 RPM
8초  9003 RPM
9초  9038 RPM
10초 9077 RPM
테스트 전 PWM 값(0)으로 복구했습니다.
```

사용자가 최대 출력 때 팬 소리·바람이 강해졌음을 확인했다. 이 결과로 팬 회전과 속도 변경 동작을 확인했다. 이번 추론 시험 중의 CPU·Hailo 온도 로그는 수집하지 않았으므로, 쿨러 설치 전후의 냉각 성능이나 장시간 추론 시 온도 안정성은 아직 비교하지 않았다.

## 7. 서멀 모니터 개선

액티브 쿨러 설치에 맞춰 [`thermal_monitor.py`](../Raspi5_vision/tools/thermal_monitor.py)를 개선했다.

- CPU 온도 옆에 팬 상태와 RPM 표시. 좁은 터미널에서는 팬을 별도 행으로 표시.
- `RUNNING`, `STOPPED`, PWM 출력 중 회전수 0인 `CHECK`, 조회 실패 `N/A`를 구분.
- 팬 장치 이름으로 센서를 찾으므로 `hwmon` 번호가 바뀌어도 조회 가능.
- 화면 크기에 맞춰 각 행을 고정 위치에 갱신. 화면 아래쪽·오른쪽 끝 출력과 새 줄 누적을 피하도록 변경.
- 별도 터미널 화면에서 실행하고 종료 시 원래 화면·커서를 복원.
- 팬 제어 파일에 값을 쓰지 않으며, 기존 자동 팬 제어를 유지.
- 터미널이 아닌 출력은 기본 한 번만 표시. 반복 파일 기록은 `--log`로 명시.

Pi에서 새 코드를 받은 뒤, 별도 PuTTY 터미널에서 실행할 명령은 다음과 같다. `watch`로 감싸지 않는다.

```bash
cd "$HOME/Desktop/kimGA_raspi/microprocessor-capstone-design/03. 김가네 캡스톤 디자인/Raspi5_vision"
python3 tools/thermal_monitor.py --screen
```

화면 예시의 숫자는 가상값이다. 실제 센서 결과와 혼동하지 않도록 `--demo` 실행에는 `SIMULATED`를 표시한다.

```text
CPU    46.5 °C  █████████░░░░░░░░░░░  |  FAN RUNNING 2726 RPM
HAILO  54.2 °C  ███████████░░░░░░░░░
```

개발 PC에서 관련 테스트 **21개와 subtest 23개**, Ruff·Mypy 검사를 통과했다. 팬 장치 탐색, 센서 실패·정지 구분, 화면 크기 변경·한글 폭 처리, 갱신 시 새 줄 미출력, 예외·Ctrl+C 종료 복원을 확인했다. **개선한 모니터의 실제 Pi·PuTTY 실행은 아직 미확인**이며, 앞 절의 실제 팬 시험과 구분한다. 센서 조회 근거는 [Linux pwm-fan 문서](https://docs.kernel.org/hwmon/pwm-fan.html)를 참고한다.

## 8. 재실행 시 주의 사항과 관련 자료

`/tmp/kimgane-khs-check`의 모델·라벨은 임시 파일이다. 재부팅 등으로 사라지면 다시 준비해야 한다. 시험 도구는 파일이 없거나 비어 있으면 시작 전에 오류를 내며, 모델을 자동 다운로드하지 않는다. 다른 위치의 준비된 파일은 `--model`, `--labels`로 지정할 수 있다.

300프레임과 180초는 실행 제한이다. 이번에는 사용자가 먼저 종료했으므로 300프레임 완주나 180초 연속 동작을 확인한 것으로 기록하지 않는다.

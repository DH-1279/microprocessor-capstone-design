## 3. 손 인식

### 3-1. 하는 일

`vision.MediaPipeHandTracker`를 대체한다. 설정 키와 호출 계약은 같다.

```python
from KMJ_hand_audio_ui.hand_tracker import HandTracker

with HandTracker(config["vision"]) as tracker:
    hand = tracker.detect(rgb, captured_at, frame_id)
```

**대표점** — 손목과 네 손가락 뿌리 관절(0, 5, 9, 13, 17)의 평균이다. 원본 영상 기준 0~1 정규화 좌표다. 손가락을 움직여도 흔들리지 않는 지점이라 방향·근접도 계산에 쓴다.

**좌우 판단** — 설정한 손만 받는다. 두 손이 잡히거나 같은 손이 둘이면 모호하므로 `None`을 돌려준다. 좌표가 범위를 벗어나거나 관절이 21개가 아니어도 받지 않는다.

**프레임 식별** — `frame_id`를 함께 받는다. 같은 번호나 더 오래된 번호가 들어오면 오류를 낸다. 병렬 추론을 넣을 때 물체 인식과 손 인식이 다른 시점의 결과를 섞지 않게 하기 위한 것이다. 넘기지 않아도 동작하므로 기존 두 인자 호출도 유지된다.

**카메라를 열지 않는다.** 공통 파이프라인이 한 번 연 프레임을 받는다.

### 3-2. 보정을 넣은 이유

2026-10-07 측정(노트북 웹캠, `hand_landmarker.task`, 면장갑, 오른손).

| 자세 | 맨손 | 분홍 | 흰색 | 검정 |
|---|---:|---:|---:|---:|
| 손등 | 100% | 100% | — | 100% |
| 손바닥 | 100% | 100% | — | 100% |
| 세운 손 | 99.6% | 32.8% | 36.2% | 0.0% |

**손등·손바닥은 색상과 무관하게 100%다.** 세운 손에서만 무너지며, 검정 장갑은 283프레임 중 0프레임이었다.

그리고 **장갑을 끼고 손을 완전히 펴면 좌우 판정이 흔들린다.** 분홍과 검정 모두에서 오른손이 `Left`로 나왔고, 손가락을 살짝 구부리면 제대로 잡았다. `vision.hand`가 `Right`이므로 뒤집힌 프레임은 버려지고 안내가 멈춘다. 랜드마크 자체는 정상인데도 그렇다.

**최근 프레임을 모아 다수결로 판정한다.** 새 답이 이기려면 차이가 벌어져야 하므로 한 프레임이 뒤집혀도 결과가 바뀌지 않는다.

**짧은 소실은 마지막 측정점을 유지한다.** 물건을 집으려고 손을 기울이면 세운 손 조건이 되는데, 거기서 안내가 끊겼다 붙었다 하는 것을 줄인다. 기본 400ms이고, 측정된 적 없는 손은 유지하지 않는다. 컨트롤러의 프레임 만료와 목표 확인은 그대로 적용된다.

`stats().hold_ratio`로 보정이 얼마나 개입했는지 볼 수 있다.

측정 기록: `docs/2026-10-07_KMJ_장갑_손인식률_측정.md`

### 3-3. vision.py 연결

```python
from KMJ_hand_audio_ui.hand_tracker import HandTracker

# run_vision 안
tracker = resources.enter_context(HandTracker(config))
hand = tracker.detect(rgb, captured_at, frame_id)
```

설정을 추가하지 않으면 기본값으로 동작한다. `hand_stability.hold_ms: 0`으로 두면 유지가 꺼진다.

**보정 전후를 비교해 측정한 뒤에 켜는 것을 제안한다.** 유지가 과하면 이미 사라진 손으로 안내하게 되므로, 실제 장갑으로 `hold_ratio`를 보고 정하면 좋겠다.

## 4. STT

### 4-1. 하는 일

녹음, 발화 구간 검출, whisper-cli 호출은 `audio.py`가 한다. 이 모듈은 그 출력을 명령으로 바꾼다.

```python
from KMJ_hand_audio_ui import speech

intent = speech.parse_input(text, targets, state)
```

**오인식 보정** — 어절을 자모로 쪼개 가장 가까운 명령을 찾는다. 2026-10-12 측정에서 실제로 나온 출력이다.

```
컴 찾아줘 -> cup        눈병 찾아줘 -> bottle    물농 찾아줘 -> bottle
휴데폰    -> cell phone 마우스 타자줘 -> mouse   전지       -> stop
모른 쪽   -> right      컵찾아줘    -> cup
```

**잘못된 발화 거부** — 문장의 모든 어절이 명령 문법에 맞아야 받는다.

| 입력 | 결과 |
|---|---|
| 책상 정리했어 | 거부 (unknown_word) |
| 컵 말고 책 | 거부 (negation) |
| 컵이랑 책 | 거부 (multiple_targets) |
| 마우스패드 | 거부 |
| 컵 정지 | 거부 (mixed_command) |

어절 안에서만 보정하므로 "책상"은 "책"이 되지 않는다. 현재 `controller._request()`의 부분 문자열 판정이 위험했던 지점이 거기다.

**상태별 제한** — 안내 중에는 새 목표를 받지 않고, 손 복구 대기에서는 "계속"만 받는다. 중지는 모든 상태에서 받는다.

**라벨과 별칭은 `controller.targets`에서 읽는다.** COCO 라벨(`cell phone`)과 설정의 별칭(`머그`, `생수`)이 그대로 동작하며 사전이 두 곳으로 갈라지지 않는다.

### 4-2. 모델 크기

2026-10-12 측정. 데스크톱 + ZEALSOUND K66S-C, faster-whisper, 명령 9종 각 3회.

| 모델 | 성공률 | 목록 제외 | 평균 인식 시간 |
|---|---|---|---|
| tiny | 26/27 (96.3%) | 24/24 (100%) | 0.24초 |
| base | 26/27 (96.3%) | 24/24 (100%) | 0.44초 |

**성공률이 같고 tiny가 두 배 빠르다.** 유일한 실패가 "목록"이고 tiny·base 모두 틀렸으므로 모델 크기 문제가 아니다.

STT 문장 정확도는 55.6%였고 명령 인식 성공률은 100%였다. 보정 계층이 44.4%p를 메웠다.

**tiny 유지를 제안한다.** 다만 whisper.cpp가 아니라 faster-whisper로 측정했으므로, 인식률은 같아도 속도는 다를 수 있다.

### 4-3. controller.py 연결

`_request()`의 라벨 추출 부분만 바뀌고 나머지 로직은 그대로다.

```python
from KMJ_hand_audio_ui import speech

def _request(self, text: str, now: float) -> str:
    intent = speech.parse_input(text, self.targets, self._intent_state())
    if not intent:
        return speech.refusal_speech(intent)
    if intent.kind == "control":
        ...  # stop, list 처리는 기존과 같음
    if intent.kind == "direction":
        side, labels = intent.name, ([self.pending_label]
                                     if self.pending_label else [])
    else:
        labels, side = [intent.name], None
    # 이하 후보 선택은 기존 코드 그대로
```

바뀌는 것은 세 가지다.

- 정규식과 별칭 포함 검사를 `speech.parse_input` 호출로 대체
- `text.replace("책상", "")` 삭제. 특정 단어를 지우지 않고 문법으로 거부한다
- 거부 사유마다 다른 안내를 돌려줄 수 있다

## 5. TTS

### 5-1. 하는 일

합성과 재생은 `audio.py`가 한다. 이 도구는 음성을 미리 만들어 둔다.

`tts_cache_path()`가 `sha256("espeak-ng\0voice\0rate\0text")`로 파일명을 만들고 파일이 있으면 재사용하므로, **같은 규칙으로 미리 WAV를 넣어두면 실행 중에 합성하지 않는다.** 파이에서 espeak 프로세스가 뜨지 않고 첫 발화 지연이 사라진다.

```
python -m KMJ_hand_audio_ui.tools.prebuild_tts
python -m KMJ_hand_audio_ui.tools.prebuild_tts --list
```

문장은 `controller.targets`에서 만들고, 조사는 받침에 따라 갈린다. 컵을/마우스를, 책이/마우스가.

`audio.tts_voice`나 `tts_rate`를 바꾸면 캐시 키가 바뀌므로 다시 만들어야 한다.

### 5-2. 음질

eSpeak NG 한국어는 알아듣는 데 문제는 없으나 기계음에 가깝다. 사용자가 시각장애인이고 음성이 주 정보 채널이므로 더 자연스러운 엔진을 쓸 여지는 있다.

Piper를 검토했으나 지금 쓰기 어렵다. 2024년 12월 한국어 지원 요청에 2025년 9월에야 커뮤니티 모델 링크 하나가 달렸고, 2026년 7월 자료도 Piper 커뮤니티가 한국어에 쓸 만한 음성을 만들지 못했다고 기술한다. 유일한 모델(neurlang/piper-onnx-kss-korean)은 추론에 Rust 구현이 필요하고 음소 처리가 표준 Piper와 다르며 라이선스가 cc-by-nc-sa-4.0이다.

사전 생성 구조에서는 합성 엔진이 파이에서 돌 필요가 없으므로, 나중에 더 나은 엔진을 쓰더라도 `audio.py` 변경 없이 WAV만 교체하면 된다.

## 6. 화면

### 6-1. 하는 일

BLE 전송과 같은 계약을 쓴다.

```python
transmit_loop(config["ble"], lambda: tuple(latest), stop, on_connection)
serve(lambda: tuple(latest), on_text, thread_stop, targets)
```

**같은 Decision을 읽으므로 화면이 장갑과 다른 상태를 보여줄 수 없다.** 버튼은 `on_text`로 들어가 음성과 같은 경로로 컨트롤러에 도달한다. 화면은 별도 목표 상태를 갖지 않고 모터를 직접 켜지 않는다.

**화면은 부가 기능이다.** fastapi/uvicorn이 없으면 메시지만 남기고 넘어가고, 브라우저가 끊겨도 안내는 계속된다. 메인 루프를 막지 않도록 별도 스레드에서 돈다.

### 6-2. 구성

2026-10-07 시안(`docs/prototypes`)의 색·간격·용어·화면낭독기 처리를 따랐다. 시안은 가상 장면으로 흐름을 확인하는 것이고, 이 화면은 실행 중인 프로그램의 Decision을 그대로 표시한다.

지금 상태 → 고른 물건 → 할 수 있는 것 → 물건 고르기 순서다.

상태에 따라 버튼이 바뀐다. 안내 중에는 물건 버튼이 꺼지고 이유를 알린다. 중지는 모든 상태에서 보인다. `near`에서만 "찾았어요"가 나온다.

**개발용 수치는 이 화면에 두지 않았다.** 명세 1장의 "사용자 화면과 개발 점검 화면을 구분한다"를 따랐다. 상태·사유·채널 값은 터미널 출력으로 확인한다.

### 6-3. 색과 대비

**저시력 사용자를 기준으로 고대비 다크 모드를 기본값으로 두었다.**

흰 배경은 빛 번짐과 눈부심을 만든다. 노랑은 망막이 가장 민감하게 반응하는 파장대라 어두운 배경 위에서 잘 보인다. 주변 시야가 좁거나 눈부심에 약한 경우에도 어두운 배경이 낫다.

| 조합 | 대비비 |
|---|---:|
| 검정 `#000` + 노랑 `#FFD400` | 14.7:1 |
| 검정 `#000` + 흰색 `#FFF` | 21.0:1 |
| 패널 `#111` + 노랑 `#FFD400` | 13.2:1 |
| 노랑 버튼 + 검정 글자 | 14.7:1 |
| 노랑 배경 `#FFE800` + 검정 글자 | 16.8:1 |

WCAG 2.2 AA의 일반 텍스트 기준은 4.5:1이다. 연한 색끼리의 조합과 비슷한 명도의 조합은 쓰지 않았다.

밝은 화면이 필요한 경우를 위해 노랑 배경 + 검정 글자를 선택지로 두었다. 모든 버튼에 4px 이상의 테두리를 둬서 경계를 뚜렷하게 했다.

기본 글자 22px에 4단계 조절, 버튼 최소 64px, 키보드 조작, 건너뛰기 링크, `role=status`로 상태 변화만 전달, 색만으로 상태를 구분하지 않고 글자를 함께 씀, 520px 아래에서 세로 배치, 강제 색상 모드 대응.

**이 색 조합은 문헌을 근거로 고른 것이고 당사자 확인은 하지 않았다.** 질환에 따라 선호가 다를 수 있으므로 실제 사용자 평가가 필요하다.

## 8. 남은 문제

### 연결

**공통 파일이 아직 이 모듈들을 쓰지 않는다.** `vision.py`는 `MediaPipeHandTracker`를, `controller.py`는 부분 문자열 판정을 그대로 쓰고 있다. 연결 방법은 3-3, 4-3, 6-4에 적었다. 담당 파일이 아니라 상의 후에 진행하겠다.

### 검증

**라즈베리파이에서 아무것도 실행하지 못했다.** 작업 시점에 연결되어 있지 않았다.

**파이 가상환경에서 `mediapipe` import가 되는지 확인하지 못했다.** `hand_tracker.py`가 이것에 의존한다. 10월 12일 기록에 "프로젝트 가상환경에서 SDK import/API 검사"가 아직 할 일로 되어 있다. 아래로 확인할 수 있다.

```
python -c "import mediapipe; print(mediapipe.__version__)"
```

**`fastapi`와 `uvicorn`이 파이에 없다.** 화면을 띄우려면 설치해야 한다. 없어도 본체는 그대로 동작하도록 만들었다.

**Camera Module 3와 AI HAT+ 2에서의 손 인식률을 모른다.** 웹캠 측정과 화질·시야각·조명이 다르다.

**whisper.cpp 실측이 없다.** STT 측정은 faster-whisper로 했다.

**모터와 PCB가 부착된 장갑에서의 인식률을 모른다.** 측정에 쓴 장갑에는 부착물이 없었다.

**`hold_ms` 기본값이 적절한지 모른다.** 과하면 이미 사라진 손으로 안내하게 된다. 실제 장갑으로 `hold_ratio`를 보고 정해야 한다.

**실제 화면낭독기 발화와 당사자 사용을 확인하지 못했다.** UX 명세 UX-10은 아직 수행하지 않았다.

### 기능

**손이 화면 밖으로 나간 것과 가려진 것을 구분하지 못한다.** 둘 다 `None`이다. 사용자에게는 다른 안내가 필요하다. 화면 밖이면 "손을 카메라 안으로 가져와 주세요", 가려진 것이면 "손이 물체에 가렸어요"가 맞다.

구분하려면 손이 마지막으로 어디서 사라졌는지 봐야 한다. 가장자리면 화면 밖, 가운데면 가려짐으로 판단할 수 있다. 다만 `Hand`에 필드를 더해야 하므로 공통 타입 변경이 필요하다. 구성안 6장에 "새 필드가 필요하면 공통 타입 변경을 먼저 검토한다"고 되어 있어 상의가 필요하다.

**"목록"이 STT에서 자주 실패한다.** 2026-10-12 측정에서 tiny·base 모두 3회 중 1회 틀렸고 다른 8개 명령은 전부 맞았다. "리스트"로 말하면 둘 다 성공한다. `speech.py`에 둘 다 별칭으로 넣었으니 사용자 안내만 "리스트"로 하면 된다.

**eSpeak NG 한국어 음질이 아슬아슬하다.** 5-2 참조.

**세운 손은 보정으로 해결되지 않는다.** `hold_ms`는 짧은 소실을 메울 뿐이다. 밝은 색 장갑과 표면 무늬 없는 재질이 함께 필요하다. 2026-10-07 측정에서 장갑 바닥의 도트 무늬를 제거하자 인식이 개선되었다.

### 부품

**USB 마이크와 스피커가 아직 없다.** 실시간 발화 구간 검출, 잡음 환경 대응, 스피커 소리의 재입력 방지를 측정하지 못했다. 확보 전까지는 `console_check.py`로 명령 경로만 확인한다.

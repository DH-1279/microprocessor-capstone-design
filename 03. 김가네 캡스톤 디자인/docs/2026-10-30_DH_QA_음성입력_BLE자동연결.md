# QA 개선: 음성 입력 준비 안내와 BLE 자동 연결

- 작성일: 2026-10-30 · 작성자: DH
- 작업 브랜치: `DH-1279/2026-10-30`
- 기준: `KimGA_raspi/2026-10-27`의 `f1661ad` (실기기 성공 코드와 10월 29일 회고 포함)
- 반영 범위: **개인 브랜치에서만 개발·검증. main과 김가네 브랜치에는 병합하지 않는다.**
- ESP 펌웨어: 변경 없음. 기존 `caps=07` 펌웨어와 350ms 두 번 획득 알림을 유지한다.

## 1. QA에서 확인한 불편

1. 캡스톤이 `kept stone` 등으로 인식되면 시동어가 수락되지 않았다.
2. TTS가 끝나도 입력 억제 시간이 남아 있어 사용자가 말할 시점을 알기 어려웠다.
3. ESP 전원이 없으면 앱 초기화가 실패했다. 연결 중단 후에는 터미널의 reconnect/resume이 필요했다.
4. 손가락별 진동 의미와 획득 알림을 처음 사용하는 사람이 알기 어려웠다.

## 2. 시동어와 물체 이름

한국어 STT 설정 `-l ko`는 기존부터 적용돼 있었다. 이를 유지하면서 아래 처리를 추가했다.

- Unicode 정규화, 영문 대소문자, 공백·구두점을 정리한다.
- 시동어 대기에서 `kept stone`, `keptstone`, `capstone`, `cap stone`을 명시적인 별칭으로 허용한다. 한글 띄어쓰기와 기존 유사 발음 비교도 유지한다.
- 부정문과 정지 명령을 포함한 발화를 시동어로 수락하지 않는다. 영문 전체에 무제한 유사도 비교를 적용하지 않는다.
- 물체 라벨의 영문 대소문자를 통일하고, `cell phone` 같은 등록된 여러 단어 별칭을 문장 분석 전에 처리한다. 반환 라벨의 원래 대소문자는 유지해 탐지 라벨과 일치시킨다.
- 기존 문법의 부정문·복수 목표·알 수 없는 문장 거부는 유지한다.
- STT 원문과 정규화 결과를 콘솔에 표시한다. 녹음 파일을 영구 저장하지 않는다.

앱이 설치된 whisper-cli의 `--help`를 확인해 `--prompt` 지원 여부를 감지한다. 지원하면 상태별로 시동어, 물체 이름, 안내 명령의 짧은 한국어 힌트를 전달한다. 미지원이면 해당 옵션을 보내지 않고 별칭 처리로 동작한다. 모델 교체나 추가 학습은 하지 않았다.

힌트와 별칭은 인식률을 보장하지 않는다. Pi의 실제 마이크·배경 소음에서 정확도와 오작동을 확인해야 한다.

## 3. 말할 타이밍 안내

```text
TTS 재생 → 잔향 대기 → 짧은 준비음 → 입력 가능
사용자 발화 → STT 처리 → 응답 또는 다음 준비음
```

- 첫 안내: “시스템이 준비되었습니다. 짧은 소리가 끝나면 말씀해주세요. 캡스톤이라고 말씀해주세요.”
- 기존 잔향 대기 기본 300ms를 유지한다.
- 준비음은 로컬에서 생성하는 80ms WAV다. 별도의 TTS 합성이나 새 라이브러리가 필요 없다.
- 준비음과 약 50ms의 꼬리 대기까지 마이크 입력을 억제하고, 이전 PCM/VAD 버퍼를 비운 뒤 입력을 연다.
- TTS가 여러 개 예약돼 있으면 안내 사이에 준비음을 넣지 않고 마지막 안내 후에만 넣는다.
- STT 중에는 새 안내를 재시도 큐에 보관한다. 중요한 안내가 `say()` 실패로 바로 사라지는 것을 줄인다.
- 동일한 대기 음성의 중복 예약을 막고 큐 크기를 제한한다.
- 앱 상태가 바뀌면 이전 상태의 수집 중 음성·버퍼·늦게 끝나는 인식 결과를 무효화한다.

화면에는 `Audio: SPEAKING / PROCESSING / LISTENING / READY / PREPARING / STOPPED` 상태가 표시된다. READY가 입력 가능한 상태다. 기존 listening 속성은 실제 발화·처리를 나타내므로 입력 가능 상태와 분리했다.

실물 스피커의 잔향이나 USB 오디오 지연은 모의 시험으로 확정할 수 없다. 준비음 직후 첫 음절이 잘리는지와 준비음이 다시 STT로 인식되는지 확인해야 한다. TTS 도중 사용자 음성을 동시에 받아들이는 기능은 이번 변경 범위에 포함하지 않았다.

## 4. BLE 자동 연결과 복구

```text
로컬 송신 작업 준비 → 영상·음성·화면 실행
                        ↕
              BLE 검색 → 연결·초기 STOP·기능 확인
                        ↓
              새 손 프레임으로 진동 안내
                        ↓
                연결 중단 → 자동 재시도
```

- ESP가 없어도 로컬 IPC 작업이 준비되면 앱 초기화를 계속한다. 연결 완료를 기다리며 영상·음성을 막지 않는다.
- 처음 미연결이면 “장갑이 연결되지 않았습니다. 연결을 기다립니다.”라고 안내한다.
- 연결되면 “장갑이 연결되었습니다.”, 끊기면 “장갑 연결이 끊겼습니다. 자동으로 다시 연결합니다.”라고 안내한다.
- 검색·연결은 한 작업에서 순차 실행하며 각 시도에 시간 제한을 둔다. 실패 후 대기는 기본 2 → 4 → 8 → 최대 10초다. 검색/연결 자체의 소요 시간은 별도다.
- 진동 안내가 없는 대기 상태에서도 약 2초마다 상태를 읽어 전원 차단을 감지한다. 이 읽기는 1초로 제한한다. 안내 중에는 기존 명령 쓰기로 실패를 감지한다.
- 같은 상태의 반복 재시도로 TTS를 계속 재생하지 않는다. 빠르게 연결 상태가 반복될 때도 같은 상태 음성은 10초 이내 재예약을 제한한다.
- 펌웨어 불일치는 앱을 종료하는 대신 업데이트 안내와 오류 로그를 남기고 재확인한다. 기능 확인을 통과하기 전 모터 ON을 보내지 않는다.

### 재연결 후 재개 조건

연결 직후에는 초기 STOP과 기능 확인을 마친 뒤 기존 안내 좌표를 비운다. 연결 이후 캡처한 유효한 새 손 프레임으로 안정화한 뒤에만 자동 안내한다.

- 탐색 중이고 새 관측이 유효하면 자동 재개한다.
- 터미널에서 직접 stop한 상태는 재연결해도 정지 상태를 유지한다.
- 음성 취소로 시동어 대기로 돌아갔다면 진동을 자동으로 시작하지 않는다.
- 연결 전·연결 중단 동안 발생한 획득 이벤트와 모터 시험은 나중에 재생하지 않는다.
- 명시적 종료나 Ctrl+C는 검색/연결 대기 중에도 작업을 취소한다.

일반 사용에서는 reconnect/resume 입력이 필요 없다. 기존 수동 연결 흐름은 `--manual-reconnect` 점검 옵션으로 남겼다. 이 옵션에서는 초기 연결 대기와 수동 재개 방식이 유지된다.

`--no-ble`은 BLE 없이 영상·음성만, `--dry-run`은 실제 연결·모터 출력 없이 모의 송신을 실행한다. 모의 모드에서는 실제 장갑 연결과 구분되는 안내를 한다.

## 5. 진동 역할 설명

처음 물체를 선택하면 다음 안내를 함께 재생한다.

> 지갑을 찾아 안내합니다. 엄지는 오른쪽, 새끼는 왼쪽, 검지는 앞, 약지는 뒤, 중지는 근접입니다. 획득하면 전체가 두 번 울립니다.

두 번째 선택부터는 다음과 같이 줄인다.

> 컵을 찾아 안내합니다. 진동을 따라 움직이세요. 획득하면 전체가 두 번 울립니다.

“설명”, “도움말”, “사용법”으로 전체 역할을 다시 들을 수 있다. 방향 계산은 기존 손 좌표계 기준을 유지한다. 화면에 고정된 좌우를 기준으로 설명하는 방식으로 바꾸지는 않았다.

## 6. 개인 브랜치에서 실행

기존 detector를 Ctrl+C로 종료하고, Pi 저장소에서 개인 브랜치를 선택한다. 작업 중인 파일이 있어 Git이 전환을 거부하면 강제로 버리지 않는다.

```bash
cd "$HOME/Desktop/kimGA_raspi/microprocessor-capstone-design"
git fetch origin
git switch DH-1279/2026-10-30
git pull --ff-only origin DH-1279/2026-10-30

cd "03. 김가네 캡스톤 디자인/Raspi5_vision"
source .venv/bin/activate
export DISPLAY=:0
python -u KHS_KMJ_vision/detector.py --address 9C:CC:01:82:75:8A --mode 3 --reach-px 75 --reach-frames 8
```

ESP 재업로드는 필요 없다. 현재 `caps=07` 펌웨어를 사용한다. 사용자가 실기기 시험으로 정한 실행 조건인 **75px / 8개 연속 유효 프레임 / DISPLAY=:0**을 운영 기준으로 삼는다. 코드 기본값 50px/5프레임을 변경하지 않아도 위 옵션이 우선 적용된다. mode 3 방향 계산과 다섯 모터 최대 PWM 350ms 두 번 알림은 유지한다. 이 옵션의 선정과 새 QA 변경의 실기기 검증 여부는 구분한다.

## 7. QA 확인 순서

| 시험 | 기대 결과 |
|---|---|
| ESP 전원을 끄고 앱 실행 | 화면·음성이 시작되고 장갑 연결 대기 안내 |
| 이후 ESP 전원 ON | 자동 연결, 연결 안내, 새 프레임부터 안내 가능 |
| 대기 중 ESP 전원 OFF/ON | 다음 상태 검사에서 감지하고 자동 복구 |
| 탐색 중 연결 중단/복구 | 진동 중단 후 새 손 좌표로 자동 재개 |
| 직접 stop 후 연결 중단/복구 | 직접 resume하기 전까지 모터 OFF |
| 미연결 상태에서 획득 후 연결 | 이전 완료 진동을 뒤늦게 재생하지 않음 |
| 준비음 전후 발화 | 준비음이 끝난 뒤 말한 명령이 수락되는지 확인 |
| 캡스톤 / kept stone / capstone | 시동어 대기에서 수락 |
| 캡스톤 말고 / 정지 / 무관한 영어 문장 | 시동어로 오인하지 않음 |
| 영문 Wallet / cell phone | 등록된 물체 라벨로 판정 |
| 첫 목표 / 다음 목표 / 설명 | 전체 설명 → 짧은 설명 → 전체 설명 재생 |

## 8. 검증 범위

호스트에서 기존 실기기 성공 버전의 회귀 검사와 새 QA 검사를 함께 실행한다. 실제 C++ 패턴 엔진을 포함한 88개 검사가 통과했다. BLE 대기·재연결은 모의 BLE 백엔드와 실제 localhost UDP/비동기 작업으로 검증했고, 준비음 WAV 형식과 재생 중 PCM 억제·준비 상태 순서, 별칭·부정문, 문법을 검사했다. 정적 검사와 ESP 코드 미변경 여부도 확인한다.

실제 Pi의 Bluetooth, 마이크·스피커, 주변 잡음, STT 처리 시간, 착용 상태에서의 안내는 아직 이 브랜치로 검증하지 않았다. 따라서 개인 브랜치에서 위 순서대로 실기기 QA 후 병합 여부를 판단한다.
